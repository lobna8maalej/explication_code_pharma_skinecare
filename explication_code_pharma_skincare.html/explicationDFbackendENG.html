Explanation of the Pharma Platform Backend

1. JWT Authentication Middleware

The authentication middleware protects the application's routes. It checks that the user has a valid JWT token before allowing access to certain features.

The jsonwebtoken module is imported using require("jsonwebtoken"). It is used to verify JWT tokens sent by the frontend.

2. auth Function

The auth function is middleware executed before certain controllers. Its role is to verify the user's identity.

The middleware retrieves the HTTP Authorization header using req.headers.authorization.

The frontend should normally send information in this format:

Authorization: Bearer TOKEN_JWT

If no Authorization header is sent, the server returns an HTTP 401 error with the message "No token provided".

The server then checks that the header starts with Bearer . This ensures that the token format is correct.

The token is then retrieved using: authHeader.split(" ")[1].

The jwt.verify() function then verifies the token using the secret key contained in the JWT_SECRET environment variable.

If the token is valid, the information contained in the token is placed in req.user.

This allows the following controllers to know which user is logged in.

Finally, next() allows the request to continue to the next middleware or controller.

3. JWT Error Handling

If the token is incorrect, expired, or invalid, an exception is generated. The catch block catches this error.

The server then returns an HTTP 401 response with the message Invalid token.

4. isAdmin Middleware

The isAdmin middleware checks whether the logged-in user has the admin role.

The condition checks:

req.user && req.user.role === "admin"

If the user is an administrator, next() allows access to the controller.

Otherwise, the server returns an HTTP 403 error. This means that the user is authenticated but does not have the necessary permissions.

5. Second Version of isAdmin

In your code, there is also a second function called isAdmin. It directly checks:

req.user.role !== "admin"

If the role is not admin, it returns a 403 error. Otherwise, it calls next().

It is preferable to keep only one version of isAdmin to avoid duplicates and import conflicts.

6. Multer Middleware

The Multer middleware manages file uploads from the frontend to the server, particularly product images.

multer.diskStorage() defines how the files will be stored on the server.

The destination property indicates that the files will be saved in the:

uploads/

folder.

The filename property generates a unique name for each image.

The name contains the current date using Date.now(), followed by the original filename.

For example, an image called vitamine.jpg may become:

1725647890000-vitamine.jpg

The function multer({ storage }) then creates the upload middleware.

7. Order Routes

The order routes file uses Express to define the different URLs related to orders.

The router is created with:

const router = express.Router();

The functions from the orderController are then imported.

8. Creating an Order

The route:

POST /api/orders

allows a new order to be created.

It uses the auth middleware. This means that only a logged-in user can create an order.

The controller called is createOrder.

9. Retrieving All Orders

The route:

GET /api/orders

allows all orders to be retrieved.

It is protected by two middlewares: auth followed by isAdmin.

This means that the user must be logged in and have the administrator role.

10. Retrieving a User's Orders

The route:

GET /api/orders/user/:userId

allows the orders associated with a specific user to be retrieved.

The route is protected by auth, but in this version the isAdmin middleware is not used.

11. Retrieving an Order

The route:

GET /api/orders/:id

allows an order to be retrieved using its MongoDB identifier.

The user must be authenticated through the auth middleware.

12. Updating an Order Status

The route:

PUT /api/orders/:id/status

allows the status of an order to be modified.

It is reserved for administrators.

The status can, for example, change from En attente to En préparation, then to Expédiée, and finally Livrée.

13. Updating the Payment Status

The route:

PUT /api/orders/:id/payment-status

allows the payment status of an order to be modified.

This operation is also reserved for the administrator.

14. Deleting an Order

The route:

DELETE /api/orders/:id

allows an order to be deleted.

This operation is protected by auth and isAdmin. A normal user therefore cannot delete an order.

15. Stripe Payment Routes

The paymentRoutes.js file contains the routes used to manage payments with Stripe.

16. Creating a Stripe Session

The route:

POST /api/payments/create-checkout-session

allows a Stripe payment session to be created.

The route uses the auth middleware. The user must therefore be logged in before making a payment.

The controller called is createCheckoutSession.

17. Retrieving Payments

The route:

GET /api/payments/admin

allows the administrator to retrieve the list of payments.

It uses auth and isAdmin.

18. Stripe Webhook

The route:

POST /api/payments/webhook

is used by Stripe to automatically send notifications to the server.

It uses express.raw() because Stripe needs the raw request body to verify the webhook signature.

The stripeWebhook controller then receives the event sent by Stripe.

19. Product Routes

The productRoutes.js file contains the routes used to manage pharmacy products.

20. Creating a Product

The route:

POST /api/products

allows an administrator to create a new product.

It uses three middlewares: auth, isAdmin, and upload.single("image").

The first verifies the user's identity. The second verifies that the user is an administrator. The third allows an image to be received.

21. Retrieving Products

The route:

GET /api/products

allows all products to be retrieved.

This route is public. No JWT token is required.

This allows visitors and customers to view the available products.

22. Updating a Product

The route:

PUT /api/products/:id

allows an administrator to modify a product.

The image is optional thanks to upload.single("image").

If a new image is uploaded, it can replace the previous image.

23. Sales Routes

The salesRoutes.js file provides access to the platform's sales statistics.

24. Overall Sales Overview

The route:

GET /api/sales/overview

allows an overall view of sales to be retrieved.

It is protected by auth and isAdmin. Only an administrator can access this information.

The controller can return, among other things, total revenue, the number of orders, and the average order value.

25. Sales by Day

The route:

GET /api/sales/by-day

allows sales grouped by day to be retrieved.

This data can then be used in an administrator dashboard to display statistical charts.

26. Settings Routes

The settingsRoutes.js file allows the general settings of the store to be managed.

27. Retrieving Settings

The route:

GET /api/settings

allows the administrator to retrieve the store settings.

It requires authentication and the administrator role.

28. Updating Settings

The route:

PUT /api/settings

allows the administrator to modify the settings.

These settings may concern the store name, email, phone number, address, currency, orders, maintenance, delivery, and Stripe.

29. User Routes

The userRoutes.js file contains routes related to authentication and customers.

30. Registration

The route:

POST /api/users/register

allows a new user to create an account.

This route is public because the user is not logged in yet.

31. Login

The route:

POST /api/users/login

allows an existing user to log in.

The server verifies the email address and password. If the information is correct, a JWT token is generated.

32. Customer List

The route:

GET /api/users/customers

allows the list of customers to be retrieved.

In the controller, only users with the user role are selected.

33. Retrieving a Customer

The route:

GET /api/users/customers/:id

allows a customer to be retrieved using their identifier.

34. Deleting a Customer

The route:

DELETE /api/users/customers/:id

allows a customer to be deleted.

Attention: in the presented code, these three customer routes are not protected by auth and isAdmin.

For a real application, it is strongly recommended to protect these routes if they are intended to be used only by the administration.

35. Python Scraper Launch Script

The code:

from scrapers.pharma_scraper import scrape_products scrape_products()

imports a function called scrape_products from the scrapers.pharma_scraper module.

The function is then executed using scrape_products().

Its purpose is to automatically start product scraping.

36. Requests Library

In the Python scraper, the requests library is used to send an HTTP request to a website.

The requests.get() function retrieves the HTML content of the page.

37. BeautifulSoup Library

BeautifulSoup is used to analyze the HTML code retrieved from the website.

With BeautifulSoup, the program can search for HTML elements containing product information.

38. Connecting to MongoDB with Python

The pymongo library allows Python to communicate with MongoDB.

The connection is established using:

MongoClient("mongodb://localhost:27017/")

The program therefore connects to a MongoDB instance installed locally on the machine.

39. pharma_db Database

The code uses the database:

pharma_db

It then uses the collection:

products

The products retrieved from the websites will be stored in this collection.

40. First Scraper: Pharma Shop

The first scraper uses the address:

https://pharma-shop.tn/

The program sends an HTTP request with a User-Agent. This makes it possible to simulate a browser when retrieving the page.

41. Product Search

The program searches for all HTML elements with the following structure:

div class="product"

Each element found is considered a product.

42. Extracting the Product Name

For each product, the program searches for the h2 tag.

The text is then retrieved using .text and cleaned using .strip().

The result is stored in the name variable.

43. Extracting the Price

The scraper then searches for a:

span class="price"

tag.

The content of this tag is retrieved and stored in the price variable.

44. Creating the Product Object

The program then creates a Python dictionary containing the name and price:

{ "name": name, "price": price }

This object represents the product information that will be stored in MongoDB.

45. Inserting into MongoDB

The collection.insert_one() function is used to insert a product into MongoDB.

After the insertion, the program displays the product name in the console using print("Inserted:", name).

46. Scraper Error Handling

The processing of each product is placed inside a try / except block.

If the scraper encounters a problem retrieving the name, price, or inserting the product, the error is caught and displayed in the console.

This allows the scraper to continue processing instead of stopping completely at the first error.

47. Second Scraper: Doppelherz

The second scraper works in a similar way, but it uses another source:

https://www.doppelherz.tn/produits

It retrieves the content of this page using requests.

Then, BeautifulSoup analyzes the HTML and searches for elements with the product class.

For each product, the program retrieves its name and price.

The information is then stored in the same MongoDB collection: pharma_db.products.

48. Direct Execution of the Scraper

The condition:

if __name__ == "__main__":

allows the scrape_and_save() function to be executed automatically when the Python file is launched directly.

This prevents the function from being automatically executed if the file is simply imported into another program.

49. General Project Architecture

The overall architecture can be represented as follows:

React Frontend ↓ Express REST API ↓ JWT Middleware ↓ Routes ↓ Controllers ↓ Mongoose Models ↓ MongoDB

For payments, an additional part is involved:

React ↓ Express ↓ Payment Controller ↓ Stripe Checkout ↓ Stripe Webhook ↓ MongoDB

For retrieving external products, the flow is different:

External Website ↓ Python Requests ↓ BeautifulSoup ↓ Scraper ↓ PyMongo ↓ MongoDB

50. Authentication Flow

When a user registers, the server creates their account and generates a JWT token.

When the user logs in, the server verifies the password and also generates a JWT token.

The frontend then stores this token and sends it with requests that require authentication.

The auth middleware verifies the token and places the user's information in req.user.

The isAdmin middleware then verifies the user's role.

51. Order Flow

The customer views the products using the public GET /api/products route.

The customer then adds products to the cart.

When the customer confirms the cart, the frontend sends a POST /api/orders request.

The JWT middleware verifies that the customer is logged in.

The createOrder controller validates the products, calculates the total amount, and creates the order in MongoDB.

52. Stripe Payment Flow

After the order is created, the frontend can request the creation of a Stripe session.

The backend verifies that the order belongs to the logged-in user.

It then creates a Stripe Checkout session containing the products and their prices.

The customer is redirected to Stripe to complete the payment.

Once the payment is completed, Stripe can send an event to the server through the webhook.

The webhook then updates the payment and the order in MongoDB.

53. Scraping Flow

The Python scripts automatically retrieve products from several pharmaceutical websites.

The scraper sends an HTTP request, analyzes the HTML page, retrieves the product information, and then saves it in MongoDB.

The data can then be retrieved by the Node.js backend and displayed in the React application.

54. Important Points to Improve

The first point concerns duplicate code. You have two versions of the isAdmin middleware. It is preferable to keep only one isAdmin function.

The second point concerns the customer routes. The /customers routes are currently public. If they are intended for the administrator dashboard, it is preferable to use:

auth, isAdmin

before the relevant controllers.

The third point concerns scraping. The HTML selectors div.product, h2, and span.price must exactly match the actual structure of the websites concerned. If the website changes its HTML, the scraper may stop working.

The fourth point concerns the price. In the scraper, the price is currently retrieved as a string. To perform calculations correctly in MongoDB or in the backend, it is preferable to clean the price and then convert it to a number.

The fifth point concerns sensitive variables. Values such as JWT_SECRET and STRIPE_SECRET_KEY must be stored in the .env file and must never be published on GitHub.

55. General Summary

The backend of this Pharma platform is built around several complementary technologies.

Node.js and Express are used to create the REST API and routes.

JWT is used to authenticate users and protect private routes.

isAdmin is used to restrict certain features to administrators.

Multer is used to receive and store product images.

MongoDB is used to store users, products, orders, payments, and settings.

Stripe is used to manage online payments.

Python Requests and BeautifulSoup are used to retrieve products from external websites.

PyMongo then allows the Python scraper to save the retrieved products directly into MongoDB.

The whole system therefore forms a complete e-commerce architecture with user management, administration, products, orders, payments, statistics, and automated retrieval of external data.
