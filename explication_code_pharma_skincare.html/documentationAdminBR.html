Explicação da Interface de Administração Pharma

1. Descrição geral

Esta parte do projeto corresponde à interface de administração da plataforma Pharma. Ela é desenvolvida com React e permite que o administrador gerencie produtos, pedidos, pagamentos, vendas, configurações e clientes.

A interface se comunica com o backend por meio do Axios. O backend fornece APIs REST desenvolvidas com Node.js e Express.

O fluxo geral é o seguinte:

React ↓ Axios ↓ API Express ↓ Controllers ↓ MongoDB

2. Componente AdminCustomers

O componente AdminCustomers representa a página que permite ao administrador consultar e excluir os clientes registrados na plataforma.

Ele utiliza os hooks do React useState e useEffect.

3. Importação de useEffect e useState

O código começa importando useEffect e useState do React.

useState permite criar e modificar os dados internos do componente.

useEffect permite executar automaticamente uma função quando o componente é carregado.

4. Importação do Axios

O Axios é utilizado para enviar solicitações HTTP ao backend.

Neste componente, o Axios é utilizado principalmente para obter a lista de clientes e excluir um cliente.

5. URL da API

A constante API contém o endereço principal do backend:

http://localhost:3000/api

Todas as solicitações deste componente utilizam esse endereço como URL base.

6. Estado customers

O estado customers contém a lista de clientes obtidos do MongoDB.

Ele é inicializado com um array vazio:

const [customers, setCustomers] = useState([]);

setCustomers permite modificar essa lista.

7. Estado loading

O estado loading permite saber se os dados ainda estão sendo carregados.

Ele começa com o valor true. Durante esse período, o usuário vê a mensagem Loading customers....

8. Estado error

O estado error permite armazenar uma possível mensagem de erro.

Se ocorrer um erro durante a comunicação com o backend, a mensagem é exibida ao administrador.

9. Função fetchCustomers

A função fetchCustomers permite obter a lista de clientes do backend.

Primeiro, ela ativa o estado de carregamento com:

setLoading(true);

Depois, redefine a mensagem de erro anterior com:

setError("");

10. Solicitação GET de clientes

O Axios envia posteriormente uma solicitação GET para:

GET /api/users/customers

O backend retorna os clientes registrados.

Se a resposta contiver success: true, a lista response.data.customers é armazenada no estado customers.

11. Tratamento de uma resposta sem clientes

Se o backend retornar uma resposta negativa, o array de clientes é redefinido e uma mensagem de erro é exibida.

Isso evita mostrar dados antigos quando a solicitação falha.

12. Tratamento de erros do Axios

O bloco catch gerencia os erros provenientes da solicitação HTTP.

O código tenta primeiro obter a mensagem enviada pelo backend por meio de: error.response?.data?.message.

Se nenhuma mensagem existir, uma mensagem de erro geral é exibida.

13. Bloco finally

O bloco finally é executado tanto quando a solicitação é bem-sucedida quanto quando ocorre uma falha.

Ele permite desativar o estado de carregamento por meio de:

setLoading(false);

14. useEffect para carregar os clientes

O hook useEffect chama automaticamente fetchCustomers() quando a página é carregada.

O array vazio [] significa que essa função é executada apenas uma vez quando o componente é montado.

15. Exclusão de um cliente

A função handleDelete permite excluir um cliente. Ela recebe o ID do MongoDB do cliente.

16. Confirmação antes da exclusão

Antes de excluir o cliente, o código utiliza:

window.confirm(...)

Uma janela de confirmação pergunta ao administrador se ele realmente deseja excluir o cliente.

Se o administrador decidir cancelar, a função é interrompida imediatamente.

17. Solicitação DELETE

Se o administrador confirmar, o Axios envia uma solicitação DELETE para:

DELETE /api/users/customers/:id

O ID do cliente é incluído na URL.

18. Exclusão imediata no React

Quando o backend confirma a exclusão, o cliente também é removido do array do React.

O código utiliza a função filter() para manter todos os clientes, exceto aquele que acabou de ser excluído.

Isso permite atualizar imediatamente a interface sem precisar recarregar toda a página.

19. Estado Loading em AdminCustomers

Quando loading é igual a true, o componente exibe uma página simples que contém o título Customers e a mensagem Loading customers....

20. Estado Error em AdminCustomers

Quando o estado error contém uma mensagem, a página exibe uma seção de erro.

Um botão Retry permite ao administrador chamar novamente fetchCustomers() para repetir a solicitação.

21. Exibir o número de clientes

Quando os dados são carregados, o componente exibe o número total de clientes por meio de:

customers.length

Isso permite que o administrador saiba imediatamente o número de clientes armazenados no banco de dados.

22. Exibir quando não há clientes

Se o array customers estiver vazio, o componente exibe No customers.

Ele também indica que nenhum usuário com a função user foi encontrado.

23. Tabela de clientes

Quando existem clientes, eles são exibidos em uma tabela HTML.

A tabela contém as colunas ID, Username, Email, Role, Registration e Actions.

24. Função map

A função map() percorre todos os clientes e cria uma linha HTML para cada cliente.

Cada linha utiliza como chave o ID exclusivo do MongoDB do cliente.

25. Exibir o ID

O código utiliza:

customer._id.slice(-8)

Isso permite exibir somente os últimos oito caracteres do ID do MongoDB para tornar a tabela mais fácil de ler.

26. Exibir o username

O nome de usuário é exibido por meio de:

customer.username

Ele é colocado dentro de uma tag strong para destacá-lo.

27. Exibir o email

O endereço de e-mail do cliente é exibido por meio de:

customer.email

28. Exibir a função

A função é exibida dentro de um badge por meio de:

customer.role

Nesta página, os clientes recuperados normalmente possuem a função user.

29. Exibir a data de registro

O código verifica se createdAt existe. Se esse valor existir, ele é convertido em um objeto Date do JavaScript.

O método toLocaleDateString("fr-FR") permite exibir a data de acordo com o formato francês.

30. Botão Excluir

Cada linha contém um botão que permite ao administrador excluir o cliente.

Quando o administrador clica nesse botão, a função handleDelete(customer._id) é executada.

31. Componente AdminDashboard

O componente AdminDashboard representa a página principal do painel de administração.

Ele reúne várias informações importantes da loja: produtos, pedidos, pagamentos, vendas e configurações.

32. Importação do AdminNavbar

O componente importa AdminNavbar. Essa barra de navegação permite ao administrador navegar entre as diferentes páginas de administração.

33. Estado products

O estado products contém a lista de produtos obtidos da API.

O número de produtos é calculado por meio de:

products.length

34. Estado orders

O estado orders contém a lista de pedidos.

O número total de pedidos é exibido no cartão Orders.

35. Estado payments

O estado payments contém a lista de pagamentos.

Essa lista também é utilizada para calcular o número de pagamentos realizados e pendentes.

36. Estado sales

O estado sales contém três estatísticas: receita total, número de pedidos e valor médio do pedido.

Os valores iniciais são todos iguais a zero.

37. Estado settings

O estado settings contém as configurações da loja obtidas do backend.

Ele é inicializado com null porque as configurações ainda não foram carregadas no início.

38. Recuperação do token JWT

Quando o dashboard é carregado, o token é recuperado do localStorage.

localStorage.getItem("token")

Esse token permite que o frontend demonstre ao backend que o usuário está autenticado.

39. Criação do header Authorization

O token é posteriormente colocado no header HTTP Authorization.

Authorization: Bearer TOKEN

Esse formato corresponde ao funcionamento do middleware JWT do backend.

40. Recuperação de produtos no Dashboard

O dashboard envia uma solicitação GET para:

GET /api/products

Essa rota é pública no seu backend. Portanto, não é obrigatório enviar o token para essa solicitação.

A resposta é verificada para determinar se contém diretamente um array ou se os produtos estão em uma propriedade products ou data.

41. Recuperação de pedidos

O dashboard chama:

GET /api/orders

Essa rota é protegida por auth e isAdmin.

Portanto, o token JWT é enviado nos headers.

42. Recuperação de pagamentos

O dashboard chama:

GET /api/payments/admin

Essa rota é reservada aos administradores. O token JWT é enviado com a solicitação.

43. Recuperação das estatísticas de vendas

O dashboard chama:

GET /api/sales/overview

O backend calcula a receita total, o número de pedidos e o valor médio dos pedidos.

Esses valores são posteriormente armazenados no estado sales.

44. Recuperação das configurações

O dashboard chama:

GET /api/settings

Essa rota é protegida por auth e isAdmin.

As configurações recuperadas são armazenadas no estado settings.

45. Função formatMoney

A função formatMoney permite formatar os valores financeiros.

Ela utiliza toLocaleString("fr-FR") para obter um formato adaptado ao idioma francês.

O número sempre contém duas casas após a vírgula decimal.

46. Estatísticas de pagamentos realizados

A constante paidPayments utiliza a função filter() para contar os pagamentos cujo status é paid.

Ela permite exibir o número de pagamentos realizados corretamente.

47. Estatísticas de pagamentos pendentes

A constante pendingPayments faz o mesmo para os pagamentos cujo status é pending.

48. Admin Dashboard: cartão Products

O primeiro cartão do dashboard exibe o número total de produtos.

O valor exibido corresponde a:

products.length

O ícone utilizado é o ícone de uma caixa que representa os produtos.

49. Admin Dashboard: cartão Orders

O segundo cartão exibe o número total de pedidos.

O valor corresponde a:

orders.length

50. Admin Dashboard: cartão Payments

O terceiro cartão exibe o número total de pagamentos.

Ele também exibe o número de pagamentos cujo status é paid.

51. Admin Dashboard: cartão Sales

O cartão Sales exibe a receita total.

O valor vem do backend por meio da API /api/sales/overview.

O valor é formatado com formatMoney() e posteriormente exibido em TND.

52. Admin Dashboard: cartão Settings

O cartão Settings indica se a loja está atualmente ativa ou em modo de manutenção.

Se maintenanceMode for true, o dashboard exibe Maintenance.

Caso contrário, exibe Active.

O cartão também mostra se o Stripe está ativado ou desativado por meio de settings.stripeEnabled.

53. Resumo de vendas

A seção Sales Summary apresenta três informações principais.

A primeira é a receita total. A segunda é o número de pedidos pagos. A terceira é o valor médio do pedido.

54. Receita

A receita é obtida de:

sales.totalSales

Posteriormente, ela é formatada e exibida utilizando a moeda TND.

55. Pedidos pagos

O número de pedidos pagos corresponde a:

sales.totalOrders

Esse valor vem diretamente do controlador de estatísticas de vendas.

56. Valor médio do pedido

O valor médio do pedido corresponde a:

sales.averageOrder

Ele representa o valor médio de um pedido.

57. Resumo de pagamentos

A seção Payments Summary apresenta três informações: o número total de pagamentos, os pagamentos realizados corretamente e os pagamentos pendentes.

Isso permite que o administrador obtenha rapidamente uma visão do estado atual dos pagamentos.

58. Estilos do Dashboard

O componente utiliza um objeto JavaScript chamado styles para definir diretamente vários estilos CSS.

Por exemplo, styles.page define o espaçamento interno, a cor de fundo e a altura mínima da página.

styles.cards utiliza CSS Grid para organizar os cartões do dashboard em várias colunas.

59. Componente AdminNavbar

O componente AdminNavbar representa a barra de navegação da administração.

Ele permite acessar rapidamente as diferentes funcionalidades do dashboard.

60. useNavigate

O hook useNavigate do React Router permite alterar a página atual de forma programática.

Ele é utilizado principalmente aqui durante o logout.

61. Função handleLogout

A função handleLogout permite encerrar a sessão do usuário.

Ela remove o token JWT do navegador por meio de:

localStorage.removeItem("token");

Ela também remove as informações do usuário armazenadas localmente.

localStorage.removeItem("user");

Finalmente, o usuário é redirecionado para:

/auth

62. Logo Admin Panel

A barra de navegação exibe o título Admin Panel. Ele representa o espaço reservado para a administração da loja.

63. Link Dashboard

O primeiro link permite acessar:

/admin

Essa rota corresponde ao dashboard principal.

64. Link Products

O link Products redireciona para:

/admin/products

Essa página permite ao administrador gerenciar os produtos.

65. Link Orders

O link Orders redireciona para:

/admin/orders

Essa página permite consultar e gerenciar os pedidos.

66. Link Payments

O link Payments redireciona para:

/admin/payments

Essa página permite consultar os pagamentos registrados.

67. Link Sales

O link Sales redireciona para:

/admin/sales

Essa página é destinada às estatísticas comerciais.

68. Link Settings

O link Settings redireciona para:

/admin/settings

Essa página permite modificar as configurações da loja.

69. Link Customers

O link Customers redireciona para:

/admin/customers

Essa página corresponde ao componente AdminCustomers. Ela permite ao administrador consultar os clientes.

70. Botão Logout

O botão Logout chama a função handleLogout.

A função remove os dados de autenticação e redireciona o usuário para a página de autenticação.

71. Organização da navegação

A navegação permite que o administrador percorra as principais funcionalidades do painel de administração.

Dashboard Products Orders Payments Sales Settings Customers Logout

72. Comunicação entre AdminDashboard e o backend

O dashboard obtém várias categorias de dados do backend. Cada categoria corresponde a uma API diferente.

Products → GET /api/products Orders → GET /api/orders Payments → GET /api/payments/admin Sales → GET /api/sales/overview Settings → GET /api/settings

73. Comunicação entre AdminCustomers e o backend

A página Customers utiliza principalmente duas operações.

GET /api/users/customers DELETE /api/users/customers/

A primeira obtém os clientes e a segunda exclui um cliente.

74. Correspondência com o backend

As rotas do React correspondem diretamente às rotas do Express definidas no backend.

Por exemplo, a rota do Axios no frontend GET /api/orders corresponde à rota Express protegida por auth e isAdmin.

Isso significa que o backend verifica o token JWT antes de autorizar o acesso aos pedidos administrativos.

75. Segurança com JWT

O token JWT é essencial para as funcionalidades administrativas. Ele é recuperado do localStorage e enviado no header Authorization.

O middleware do backend auth verifica o token. Em seguida, isAdmin verifica se a função do usuário é realmente admin.

O princípio de segurança é, portanto: usuário autenticado → token válido → verificação da função admin → acesso ao dashboard.

76. Ponto importante sobre AdminCustomers

No seu frontend, a página Customers chama diretamente:

GET /api/users/customers

e:

DELETE /api/users/customers/:id

Nas rotas do backend que você mostrou anteriormente, essas duas rotas atualmente não utilizam nem auth nem isAdmin.

Para uma aplicação real, é recomendável proteger essas rotas para que um usuário comum não possa consultar nem excluir as contas de outros clientes.

77. Proteção recomendada das rotas Customers

As rotas de administração de clientes deveriam funcionar idealmente utilizando o mesmo princípio das demais rotas do dashboard:

router.get( "/customers", auth, isAdmin, getCustomers ); router.get( "/customers/", auth, isAdmin, getCustomerById ); router.delete( "/customers/", auth, isAdmin, deleteCustomer );

Dessa maneira, somente um administrador autenticado poderá consultar e excluir clientes.

78. Fluxo completo de administração

Quando o administrador abre o dashboard, o React carrega o componente AdminDashboard.

O componente recupera o token JWT do localStorage.

Em seguida, várias solicitações Axios são enviadas ao backend para obter produtos, pedidos, pagamentos, estatísticas e configurações.

O backend verifica as permissões quando necessário e recupera os dados do MongoDB.

Os resultados são retornados ao React. O React armazena os resultados em seus estados e depois os exibe em forma de cartões e estatísticas.

79. Fluxo completo de clientes

Quando o administrador abre a página Customers, o componente AdminCustomers é carregado.

O hook useEffect chama automaticamente fetchCustomers().

O Axios envia uma solicitação GET ao backend. O backend recupera os usuários que possuem a função user.

O React recebe a lista e a exibe em uma tabela.

Quando o administrador clica em Delete, o Axios envia uma solicitação DELETE. Após a confirmação do backend, o cliente é imediatamente removido da interface.

80. Arquitetura geral

A arquitetura desta parte da aplicação pode ser resumida da seguinte maneira:

ADMIN ↓ React Admin Panel ↓ React Router ↓ Axios ↓ Express API ↓ JWT Middleware ↓ Admin Middleware ↓ Controllers ↓ Mongoose ↓ MongoDB

81. Conclusão

Esta parte do projeto constitui o painel de administração da plataforma Pharma.

AdminNavbar permite navegar entre as diferentes páginas.

AdminDashboard fornece uma visão geral da loja com produtos, pedidos, pagamentos, vendas e configurações.

AdminCustomers permite ao administrador consultar e excluir clientes.

Axios gerencia a comunicação entre React e a API backend.

JWT fornece autenticação e permite que o backend verifique a identidade do usuário.

isAdmin garante que as operações sensíveis sejam restritas aos administradores.

Em conjunto, esses componentes fornecem uma interface de administração completa para gerenciar uma loja farmacêutica online.
