Explanation of the Pharma Administration Interface

1. General Overview

This part of the project corresponds to the administration interface of the Pharma platform. It is developed with React and allows the administrator to manage products, orders, payments, sales, settings, and customers.

The interface communicates with the backend using Axios. The backend provides REST APIs developed with Node.js and Express.

The general workflow is therefore:

React ↓ Axios ↓ Express API ↓ Controllers ↓ MongoDB

2. AdminCustomers Component

The AdminCustomers component represents the page that allows the administrator to view and delete customers registered on the platform.

It uses the React hooks useState and useEffect.

3. Importing useEffect and useState

The code begins by importing useEffect and useState from React.

useState is used to create and modify the internal data of the component.

useEffect allows a function to be executed automatically when the component is loaded.

4. Importing Axios

Axios is used to send HTTP requests to the backend.

In this component, Axios is mainly used to retrieve the list of customers and delete a customer.

5. API URL

The API constant contains the main address of the backend:

http://localhost:3000/api

All requests from this component use this address as their base URL.

6. customers State

The customers state contains the list of customers retrieved from MongoDB.

It is initialized with an empty array:

const [customers, setCustomers] = useState([]);

setCustomers is used to modify this list.

7. loading State

The loading state indicates whether the data is still being loaded.

It starts with true. During this period, the user sees the message Loading customers....

8. error State

The error state is used to store a possible error message.

If an error occurs while communicating with the backend, the message is displayed to the administrator.

9. fetchCustomers Function

The fetchCustomers function retrieves the list of customers from the backend.

It first enables the loading state with:

setLoading(true);

Then it resets the previous error message with:

setError("");

10. GET Request for Customers

Axios then sends a GET request to:

GET /api/users/customers

The backend returns the registered customers.

If the response contains success: true, the response.data.customers list is stored in the customers state.

11. Handling a Response Without Customers

If the backend returns a negative response, the customers array is reset and an error message is displayed.

This prevents old data from being displayed when the request fails.

12. Handling Axios Errors

The catch block handles errors coming from the HTTP request.

The code first tries to retrieve the message sent by the backend using: error.response?.data?.message.

If no message is available, a general error message is displayed.

13. finally Block

The finally block is executed whether the request succeeds or fails.

It is used to disable the loading state with:

setLoading(false);

14. useEffect to Load Customers

The useEffect hook automatically calls fetchCustomers() when the page is loaded.

The empty array [] means that this function is executed only once when the component is mounted.

15. Deleting a Customer

The handleDelete function is used to delete a customer. It receives the customer's MongoDB ID.

16. Confirmation Before Deletion

Before deleting the customer, the code uses:

window.confirm(...)

A confirmation window asks the administrator whether they really want to delete the customer.

If the administrator chooses to cancel, the function stops immediately.

17. DELETE Request

If the administrator confirms, Axios sends a DELETE request to:

DELETE /api/users/customers/:id

The customer's ID is included in the URL.

18. Immediate Deletion in React

When the backend confirms the deletion, the customer is also removed from the React array.

The code uses the filter() function to keep all customers except the one that has just been deleted.

This allows the interface to be updated immediately without having to reload the entire page.

19. Loading State in AdminCustomers

When loading is equal to true, the component displays a simple page containing the Customers title and the message Loading customers....

20. Error State in AdminCustomers

When the error state contains a message, the page displays an error section.

A Retry button allows the administrator to call fetchCustomers() again in order to repeat the request.

21. Displaying the Number of Customers

When the data is loaded, the component displays the total number of customers using:

customers.length

This allows the administrator to immediately know the number of customers stored in the database.

22. Display When There Are No Customers

If the customers array is empty, the component displays No customers.

It also specifies that users with the user role were not found.

23. Customers Table

When customers exist, they are displayed in an HTML table.

The table contains the columns ID, Username, Email, Role, Registration, and Actions.

24. map Function

The map() function iterates through all customers and creates an HTML row for each customer.

Each row uses the customer's unique MongoDB ID as its key.

25. Displaying the ID

The code uses:

customer._id.slice(-8)

This displays only the last eight characters of the MongoDB ID to make the table more readable.

26. Displaying the Username

The username is displayed using:

customer.username

It is placed inside a strong tag to make it more visible.

27. Displaying the Email

The customer's email address is displayed using:

customer.email

28. Displaying the Role

The role is displayed inside a badge using:

customer.role

On this page, the retrieved customers normally have the user role.

29. Displaying the Registration Date

The code checks whether createdAt exists. If this value exists, it is converted into a JavaScript Date object.

The toLocaleDateString("fr-FR") method displays the date according to the French format.

30. Delete Button

Each row contains a button allowing the administrator to delete the customer.

When the administrator clicks this button, the function handleDelete(customer._id) is executed.

31. AdminDashboard Component

The AdminDashboard component represents the main page of the administrator dashboard.

It brings together several important store-related pieces of information: products, orders, payments, sales, and settings.

32. Importing AdminNavbar

The component imports AdminNavbar. This navigation bar allows the administrator to move between the different administration pages.

33. products State

The products state contains the list of products retrieved from the API.

The number of products is then calculated using:

products.length

34. orders State

The orders state contains the list of orders.

The total number of orders is displayed in the Orders card.

35. payments State

The payments state contains the list of payments.

This list is also used to calculate the number of paid and pending payments.

36. sales State

The sales state contains three statistics: total revenue, number of orders, and average order value.

The initial values are all set to zero.

37. settings State

The settings state contains the store settings retrieved from the backend.

It is initialized with null because the settings have not yet been loaded at startup.

38. Retrieving the JWT Token

When the dashboard loads, the token is retrieved from localStorage.

localStorage.getItem("token")

This token allows the frontend to prove to the backend that the user is authenticated.

39. Creating the Authorization Header

The token is then placed in the HTTP Authorization header.

Authorization: Bearer TOKEN

This format corresponds to the JWT middleware used by the backend.

40. Retrieving Products in the Dashboard

The dashboard sends a GET request to:

GET /api/products

This route is public in your backend. Therefore, it is not mandatory to send the token for this request.

The response is then checked to determine whether it directly contains an array or whether the products are stored in a products or data property.

41. Retrieving Orders

The dashboard calls:

GET /api/orders

This route is protected by auth and isAdmin.

The JWT token is therefore sent in the headers.

42. Retrieving Payments

The dashboard calls:

GET /api/payments/admin

This route is restricted to administrators. The JWT token is sent with the request.

43. Retrieving Sales Statistics

The dashboard calls:

GET /api/sales/overview

The backend calculates total revenue, the number of orders, and the average order value.

These values are then stored in the sales state.

44. Retrieving Settings

The dashboard calls:

GET /api/settings

This route is protected by auth and isAdmin.

The retrieved settings are stored in the settings state.

45. formatMoney Function

The formatMoney function is used to format financial amounts.

It uses toLocaleString("fr-FR") to obtain a format adapted to the French language.

The number always contains two digits after the decimal point.

46. Paid Payments Statistics

The paidPayments constant uses the filter() function to count payments whose status is paid.

It therefore allows the number of successful payments to be displayed.

47. Pending Payments Statistics

The pendingPayments constant does the same thing for payments with the pending status.

48. Admin Dashboard: Products Card

The first dashboard card displays the total number of products.

The displayed value corresponds to:

products.length

The icon used is the box icon representing the products.

49. Admin Dashboard: Orders Card

The second card displays the total number of orders.

The value corresponds to:

orders.length

50. Admin Dashboard: Payments Card

The third card displays the total number of payments.

It also displays the number of payments with the paid status.

51. Admin Dashboard: Sales Card

The Sales card displays the total revenue.

The amount comes from the backend through the /api/sales/overview API.

The amount is formatted using formatMoney() and then displayed in TND.

52. Admin Dashboard: Settings Card

The Settings card indicates whether the store is currently active or in maintenance mode.

If maintenanceMode is true, the dashboard displays Maintenance.

Otherwise, it displays Active.

The card also displays whether Stripe is enabled or disabled using settings.stripeEnabled.

53. Sales Summary

The Sales Summary section displays three main pieces of information.

The first is total revenue. The second is the number of paid orders. The third is the average order value.

54. Revenue

The revenue is retrieved from:

sales.totalSales

It is then formatted and displayed using the TND currency.

55. Paid Orders

The number of paid orders corresponds to:

sales.totalOrders

This value comes directly from the sales statistics controller.

56. Average Order Value

The average order value corresponds to:

sales.averageOrder

It represents the average amount of an order.

57. Payments Summary

The Payments Summary section displays three pieces of information: the total number of payments, successful payments, and pending payments.

This allows the administrator to quickly understand the current payment status.

58. Dashboard Styles

The component uses a JavaScript object called styles to define several CSS styles directly.

For example, styles.page defines the inner spacing, background color, and minimum height of the page.

styles.cards uses CSS Grid to organize the dashboard cards into multiple columns.

59. AdminNavbar Component

The AdminNavbar component represents the administration navigation bar.

It provides quick access to the different dashboard functionalities.

60. useNavigate

The useNavigate hook from React Router allows the current page to be changed programmatically.

It is mainly used here during logout.

61. handleLogout Function

The handleLogout function is used to log the user out.

It removes the JWT token from the browser using:

localStorage.removeItem("token");

It also removes the user information stored locally.

localStorage.removeItem("user");

Finally, the user is redirected to:

/auth

62. Admin Panel Logo

The navigation bar displays the title Admin Panel. It represents the area reserved for store administration.

63. Dashboard Link

The first link provides access to:

/admin

This route corresponds to the main dashboard.

64. Products Link

The Products link redirects to:

/admin/products

This page allows the administrator to manage products.

65. Orders Link

The Orders link redirects to:

/admin/orders

This page allows the administrator to view and manage orders.

66. Payments Link

The Payments link redirects to:

/admin/payments

This page allows the administrator to view recorded payments.

67. Sales Link

The Sales link redirects to:

/admin/sales

This page is intended for sales statistics.

68. Settings Link

The Settings link redirects to:

/admin/settings

This page allows the administrator to modify the store settings.

69. Customers Link

The Customers link redirects to:

/admin/customers

This page corresponds to the AdminCustomers component. It allows the administrator to view customers.

70. Logout Button

The Logout button calls the handleLogout function.

The function removes the authentication data and redirects the user to the authentication page.

71. Navigation Organization

The navigation therefore allows the administrator to move between the main functionalities of the administration panel.

Dashboard Products Orders Payments Sales Settings Customers Logout

72. Communication Between AdminDashboard and the Backend

The dashboard retrieves several categories of data from the backend. Each category corresponds to a different API.

Products → GET /api/products Orders → GET /api/orders Payments → GET /api/payments/admin Sales → GET /api/sales/overview Settings → GET /api/settings

73. Communication Between AdminCustomers and the Backend

The Customers page mainly uses two operations.

GET /api/users/customers DELETE /api/users/customers/:id

The first retrieves the customers and the second deletes a customer.

74. Backend Correspondence

The React routes correspond directly to the Express routes defined in the backend.

For example, the Axios frontend route GET /api/orders corresponds to the Express route protected by auth and isAdmin.

This means that the backend verifies the JWT token before authorizing access to administrative orders.

75. JWT Security

The JWT token is essential for administrative functionalities. It is retrieved from localStorage and sent in the Authorization header.

The backend auth middleware verifies the token. Then, isAdmin verifies that the user's role is indeed admin.

The security principle is therefore: authenticated user → valid token → admin role verification → dashboard access.

76. Important Point Regarding AdminCustomers

In your frontend, the Customers page directly calls:

GET /api/users/customers

and:

DELETE /api/users/customers/:id

In the backend routes you previously showed, these two routes currently use neither auth nor isAdmin.

For a real application, it is preferable to protect these routes so that a normal user cannot view or delete other customers' accounts.

77. Recommended Protection for Customer Routes

The customer administration routes should ideally work using the same principle as the other dashboard routes:

router.get( "/customers", auth, isAdmin, getCustomers ); router.get( "/customers/:id", auth, isAdmin, getCustomerById ); router.delete( "/customers/:id", auth, isAdmin, deleteCustomer );

In this way, only an authenticated administrator will be able to view and delete customers.

78. Complete Administration Flow

When the administrator opens the dashboard, React loads the AdminDashboard component.

The component retrieves the JWT token from localStorage.

Then, several Axios requests are sent to the backend to retrieve products, orders, payments, statistics, and settings.

The backend checks permissions when necessary and retrieves the data from MongoDB.

The results are returned to React. React stores the results in its states and then displays them as cards and statistics.

79. Complete Customer Flow

When the administrator opens the Customers page, the AdminCustomers component is loaded.

The useEffect hook automatically calls fetchCustomers().

Axios sends a GET request to the backend. The backend retrieves users with the user role.

React receives the list and displays it in a table.

When the administrator clicks Delete, Axios sends a DELETE request. After confirmation from the backend, the customer is immediately removed from the interface.

80. General Architecture

The architecture of this part of the application can be summarized as follows:

ADMIN ↓ React Admin Panel ↓ React Router ↓ Axios ↓ Express API ↓ JWT Middleware ↓ Admin Middleware ↓ Controllers ↓ Mongoose ↓ MongoDB

81. Conclusion

This part of the project constitutes the administration panel of the Pharma platform.

AdminNavbar allows navigation between the different pages.

AdminDashboard provides an overview of the store with products, orders, payments, sales, and settings.

AdminCustomers allows the administrator to view and delete customers.

Axios handles communication between React and the backend API.

JWT provides authentication and allows the backend to verify the user's identity.

isAdmin ensures that sensitive operations are restricted to administrators.

Together, these components provide a complete administration interface for managing an online pharmaceutical store.
