Explicación de la Interfaz de Administración Pharma

1. Descripción general

Esta parte del proyecto corresponde a la interfaz de administración de la plataforma Pharma. Está desarrollada con React y permite al administrador gestionar los productos, pedidos, pagos, ventas, configuraciones y clientes.

La interfaz se comunica con el backend mediante Axios. El backend proporciona API REST desarrolladas con Node.js y Express.

El flujo general es el siguiente:

React ↓ Axios ↓ API Express ↓ Controllers ↓ MongoDB

2. Componente AdminCustomers

El componente AdminCustomers representa la página que permite al administrador consultar y eliminar los clientes registrados en la plataforma.

Utiliza los hooks de React useState y useEffect.

3. Importación de useEffect y useState

El código comienza importando useEffect y useState desde React.

useState permite crear y modificar los datos internos del componente.

useEffect permite ejecutar automáticamente una función cuando se carga el componente.

4. Importación de Axios

Axios se utiliza para enviar solicitudes HTTP al backend.

En este componente, Axios se utiliza principalmente para obtener la lista de clientes y eliminar un cliente.

5. URL de la API

La constante API contiene la dirección principal del backend:

http://localhost:3000/api

Todas las solicitudes de este componente utilizan esta dirección como URL base.

6. Estado customers

El estado customers contiene la lista de clientes obtenidos desde MongoDB.

Se inicializa con un array vacío:

const [customers, setCustomers] = useState([]);

setCustomers permite modificar esta lista.

7. Estado loading

El estado loading permite saber si los datos todavía se están cargando.

Comienza con el valor true. Durante este período, el usuario ve el mensaje Loading customers....

8. Estado error

El estado error permite almacenar un posible mensaje de error.

Si se produce un error durante la comunicación con el backend, el mensaje se muestra al administrador.

9. Función fetchCustomers

La función fetchCustomers permite obtener la lista de clientes desde el backend.

Primero activa el estado de carga con:

setLoading(true);

Después restablece el mensaje de error anterior con:

setError("");

10. Solicitud GET de clientes

Axios envía posteriormente una solicitud GET a:

GET /api/users/customers

El backend devuelve los clientes registrados.

Si la respuesta contiene success: true, la lista response.data.customers se almacena en el estado customers.

11. Gestión de una respuesta sin clientes

Si el backend devuelve una respuesta negativa, el array de clientes se restablece y se muestra un mensaje de error.

Esto evita mostrar datos antiguos cuando la solicitud falla.

12. Gestión de errores de Axios

El bloque catch gestiona los errores procedentes de la solicitud HTTP.

El código intenta primero obtener el mensaje enviado por el backend mediante: error.response?.data?.message.

Si no existe ningún mensaje, se muestra un mensaje de error general.

13. Bloque finally

El bloque finally se ejecuta tanto si la solicitud tiene éxito como si falla.

Permite desactivar el estado de carga mediante:

setLoading(false);

14. useEffect para cargar los clientes

El hook useEffect llama automáticamente a fetchCustomers() cuando se carga la página.

El array vacío [] significa que esta función se ejecuta una sola vez cuando el componente se monta.

15. Eliminación de un cliente

La función handleDelete permite eliminar un cliente. Recibe el ID de MongoDB del cliente.

16. Confirmación antes de eliminar

Antes de eliminar el cliente, el código utiliza:

window.confirm(...)

Una ventana de confirmación pregunta al administrador si realmente desea eliminar el cliente.

Si el administrador decide cancelar, la función se detiene inmediatamente.

17. Solicitud DELETE

Si el administrador confirma, Axios envía una solicitud DELETE a:

DELETE /api/users/customers/:id

El ID del cliente se incluye en la URL.

18. Eliminación inmediata en React

Cuando el backend confirma la eliminación, el cliente también se elimina del array de React.

El código utiliza la función filter() para conservar todos los clientes excepto el que acaba de ser eliminado.

Esto permite actualizar inmediatamente la interfaz sin tener que recargar toda la página.

19. Estado Loading en AdminCustomers

Cuando loading es igual a true, el componente muestra una página sencilla que contiene el título Customers y el mensaje Loading customers....

20. Estado Error en AdminCustomers

Cuando el estado error contiene un mensaje, la página muestra una sección de error.

Un botón Retry permite al administrador volver a llamar a fetchCustomers() para repetir la solicitud.

21. Mostrar el número de clientes

Cuando los datos se han cargado, el componente muestra el número total de clientes mediante:

customers.length

Esto permite al administrador conocer inmediatamente el número de clientes almacenados en la base de datos.

22. Mostrar cuando no hay clientes

Si el array customers está vacío, el componente muestra No customers.

También indica que no se encontraron usuarios con el rol user.

23. Tabla de clientes

Cuando existen clientes, se muestran en una tabla HTML.

La tabla contiene las columnas ID, Username, Email, Role, Registration y Actions.

24. Función map

La función map() recorre todos los clientes y crea una fila HTML para cada cliente.

Cada fila utiliza como clave el ID único de MongoDB del cliente.

25. Mostrar el ID

El código utiliza:

customer._id.slice(-8)

Esto permite mostrar solamente los últimos ocho caracteres del ID de MongoDB para que la tabla sea más fácil de leer.

26. Mostrar el username

El nombre de usuario se muestra mediante:

customer.username

Se coloca dentro de una etiqueta strong para resaltarlo.

27. Mostrar el email

La dirección de correo electrónico del cliente se muestra mediante:

customer.email

28. Mostrar el rol

El rol se muestra dentro de un badge mediante:

customer.role

En esta página, los clientes recuperados normalmente tienen el rol user.

29. Mostrar la fecha de registro

El código comprueba si existe createdAt. Si este valor existe, se convierte en un objeto Date de JavaScript.

El método toLocaleDateString("fr-FR") permite mostrar la fecha según el formato francés.

30. Botón Eliminar

Cada fila contiene un botón que permite al administrador eliminar al cliente.

Cuando el administrador hace clic en este botón, se ejecuta la función handleDelete(customer._id).

31. Componente AdminDashboard

El componente AdminDashboard representa la página principal del panel de administración.

Reúne varias informaciones importantes de la tienda: productos, pedidos, pagos, ventas y configuraciones.

32. Importación de AdminNavbar

El componente importa AdminNavbar. Esta barra de navegación permite al administrador desplazarse entre las diferentes páginas de administración.

33. Estado products

El estado products contiene la lista de productos obtenidos desde la API.

El número de productos se calcula mediante:

products.length

34. Estado orders

El estado orders contiene la lista de pedidos.

El número total de pedidos se muestra en la tarjeta Orders.

35. Estado payments

El estado payments contiene la lista de pagos.

Esta lista también se utiliza para calcular el número de pagos realizados y pendientes.

36. Estado sales

El estado sales contiene tres estadísticas: ingresos totales, número de pedidos y valor medio del pedido.

Los valores iniciales son todos iguales a cero.

37. Estado settings

El estado settings contiene las configuraciones de la tienda obtenidas desde el backend.

Se inicializa con null porque las configuraciones todavía no se han cargado al iniciar.

38. Recuperación del token JWT

Cuando se carga el dashboard, el token se recupera desde localStorage.

localStorage.getItem("token")

Este token permite al frontend demostrar al backend que el usuario está autenticado.

39. Creación del header Authorization

El token se coloca posteriormente en el header HTTP Authorization.

Authorization: Bearer TOKEN

Este formato corresponde al funcionamiento del middleware JWT del backend.

40. Recuperación de productos en el Dashboard

El dashboard envía una solicitud GET a:

GET /api/products

Esta ruta es pública en tu backend. Por lo tanto, no es obligatorio enviar el token para esta solicitud.

La respuesta se comprueba para determinar si contiene directamente un array o si los productos se encuentran en una propiedad products o data.

41. Recuperación de pedidos

El dashboard llama a:

GET /api/orders

Esta ruta está protegida por auth y isAdmin.

Por lo tanto, el token JWT se envía en los headers.

42. Recuperación de pagos

El dashboard llama a:

GET /api/payments/admin

Esta ruta está reservada para los administradores. El token JWT se envía con la solicitud.

43. Recuperación de estadísticas de ventas

El dashboard llama a:

GET /api/sales/overview

El backend calcula los ingresos totales, el número de pedidos y el valor medio de los pedidos.

Estos valores se almacenan posteriormente en el estado sales.

44. Recuperación de configuraciones

El dashboard llama a:

GET /api/settings

Esta ruta está protegida por auth y isAdmin.

Las configuraciones recuperadas se almacenan en el estado settings.

45. Función formatMoney

La función formatMoney permite dar formato a los importes financieros.

Utiliza toLocaleString("fr-FR") para obtener un formato adaptado al idioma francés.

El número siempre contiene dos cifras después de la coma decimal.

46. Estadísticas de pagos realizados

La constante paidPayments utiliza la función filter() para contar los pagos cuyo estado es paid.

Permite mostrar el número de pagos realizados correctamente.

47. Estadísticas de pagos pendientes

La constante pendingPayments hace lo mismo para los pagos cuyo estado es pending.

48. Admin Dashboard: tarjeta Products

La primera tarjeta del dashboard muestra el número total de productos.

El valor mostrado corresponde a:

products.length

El icono utilizado es el icono de una caja que representa los productos.

49. Admin Dashboard: tarjeta Orders

La segunda tarjeta muestra el número total de pedidos.

El valor corresponde a:

orders.length

50. Admin Dashboard: tarjeta Payments

La tercera tarjeta muestra el número total de pagos.

También muestra el número de pagos cuyo estado es paid.

51. Admin Dashboard: tarjeta Sales

La tarjeta Sales muestra los ingresos totales.

El importe procede del backend mediante la API /api/sales/overview.

El importe se formatea con formatMoney() y posteriormente se muestra en TND.

52. Admin Dashboard: tarjeta Settings

La tarjeta Settings indica si la tienda está actualmente activa o en modo mantenimiento.

Si maintenanceMode es true, el dashboard muestra Maintenance.

De lo contrario, muestra Active.

La tarjeta también muestra si Stripe está activado o desactivado mediante settings.stripeEnabled.

53. Resumen de ventas

La sección Sales Summary presenta tres informaciones principales.

La primera es el ingreso total. La segunda es el número de pedidos pagados. La tercera es el valor medio del pedido.

54. Ingresos

Los ingresos se obtienen de:

sales.totalSales

Posteriormente se formatean y se muestran utilizando la moneda TND.

55. Pedidos pagados

El número de pedidos pagados corresponde a:

sales.totalOrders

Este valor procede directamente del controlador de estadísticas de ventas.

56. Valor medio del pedido

El valor medio del pedido corresponde a:

sales.averageOrder

Representa el importe medio de un pedido.

57. Resumen de pagos

La sección Payments Summary presenta tres informaciones: el número total de pagos, los pagos realizados correctamente y los pagos pendientes.

Esto permite al administrador obtener rápidamente una visión del estado actual de los pagos.

58. Estilos del Dashboard

El componente utiliza un objeto JavaScript llamado styles para definir directamente varios estilos CSS.

Por ejemplo, styles.page define el espacio interior, el color de fondo y la altura mínima de la página.

styles.cards utiliza CSS Grid para organizar las tarjetas del dashboard en varias columnas.

59. Componente AdminNavbar

El componente AdminNavbar representa la barra de navegación de la administración.

Permite acceder rápidamente a las diferentes funcionalidades del dashboard.

60. useNavigate

El hook useNavigate de React Router permite cambiar la página actual de forma programática.

Se utiliza principalmente aquí durante el cierre de sesión.

61. Función handleLogout

La función handleLogout permite cerrar la sesión del usuario.

Elimina el token JWT del navegador mediante:

localStorage.removeItem("token");

También elimina la información del usuario almacenada localmente.

localStorage.removeItem("user");

Finalmente, el usuario es redirigido a:

/auth

72. Comunicación entre AdminDashboard y el backend

El dashboard obtiene varias categorías de datos desde el backend. Cada categoría corresponde a una API diferente.

Products → GET /api/products Orders → GET /api/orders Payments → GET /api/payments/admin Sales → GET /api/sales/overview Settings → GET /api/settings

73. Comunicación entre AdminCustomers y el backend

La página Customers utiliza principalmente dos operaciones.

GET /api/users/customers DELETE /api/users/customers/:id

La primera obtiene los clientes y la segunda elimina un cliente.

74. Correspondencia con el backend

Las rutas de React corresponden directamente a las rutas de Express definidas en el backend.

Por ejemplo, la ruta de Axios del frontend GET /api/orders corresponde a la ruta Express protegida por auth e isAdmin.

Esto significa que el backend verifica el token JWT antes de autorizar el acceso a los pedidos administrativos.

75. Seguridad con JWT

El token JWT es esencial para las funcionalidades administrativas. Se recupera desde localStorage y se envía en el header Authorization.

El middleware del backend auth verifica el token. Después, isAdmin verifica que el rol del usuario sea realmente admin.

El principio de seguridad es, por lo tanto: usuario autenticado → token válido → verificación del rol admin → acceso al dashboard.

76. Punto importante sobre AdminCustomers

En tu frontend, la página Customers llama directamente a:

GET /api/users/customers

y:

DELETE /api/users/customers/:id

En las rutas del backend que mostraste anteriormente, estas dos rutas actualmente no utilizan ni auth ni isAdmin.

Para una aplicación real, es recomendable proteger estas rutas para que un usuario normal no pueda consultar ni eliminar las cuentas de otros clientes.

77. Protección recomendada de las rutas Customers

Las rutas de administración de clientes deberían funcionar idealmente utilizando el mismo principio que las demás rutas del dashboard:

router.get( "/customers", auth, isAdmin, getCustomers ); router.get( "/customers/:id", auth, isAdmin, getCustomerById ); router.delete( "/customers/:id", auth, isAdmin, deleteCustomer );

De esta manera, únicamente un administrador autenticado podrá consultar y eliminar clientes.

78. Flujo completo de administración

Cuando el administrador abre el dashboard, React carga el componente AdminDashboard.

El componente recupera el token JWT desde localStorage.

Después, se envían varias solicitudes Axios al backend para obtener productos, pedidos, pagos, estadísticas y configuraciones.

El backend verifica los permisos cuando es necesario y recupera los datos desde MongoDB.

Los resultados se devuelven a React. React almacena los resultados en sus estados y después los muestra en forma de tarjetas y estadísticas.

79. Flujo completo de clientes

Cuando el administrador abre la página Customers, se carga el componente AdminCustomers.

El hook useEffect llama automáticamente a fetchCustomers().

Axios envía una solicitud GET al backend. El backend recupera los usuarios que tienen el rol user.

React recibe la lista y la muestra en una tabla.

Cuando el administrador hace clic en Delete, Axios envía una solicitud DELETE. Después de la confirmación del backend, el cliente se elimina inmediatamente de la interfaz.

80. Arquitectura general

La arquitectura de esta parte de la aplicación puede resumirse de la siguiente manera:

ADMIN ↓ React Admin Panel ↓ React Router ↓ Axios ↓ Express API ↓ JWT Middleware ↓ Admin Middleware ↓ Controllers ↓ Mongoose ↓ MongoDB

81. Conclusión

Esta parte del proyecto constituye el panel de administración de la plataforma Pharma.

AdminNavbar permite navegar entre las diferentes páginas.

AdminDashboard proporciona una visión general de la tienda con productos, pedidos, pagos, ventas y configuraciones.

AdminCustomers permite al administrador consultar y eliminar clientes.

Axios gestiona la comunicación entre React y la API backend.

JWT proporciona autenticación y permite al backend verificar la identidad del usuario.

isAdmin garantiza que las operaciones sensibles estén restringidas a los administradores.

En conjunto, estos componentes proporcionan una interfaz de administración completa para gestionar una tienda farmacéutica en línea.
