Explication du Backend de la plateforme Pharma

1. Middleware d'authentification JWT

Le middleware d'authentification permet de protéger les routes de l'application. Il vérifie que l'utilisateur possède un token JWT valide avant de pouvoir accéder à certaines fonctionnalités.

Le module jsonwebtoken est importé avec require("jsonwebtoken"). Il permet de vérifier les tokens JWT envoyés par le frontend.

2. Fonction auth

La fonction auth est un middleware exécuté avant certains contrôleurs. Son rôle est de vérifier l'identité de l'utilisateur.

Le middleware récupère l'en-tête HTTP Authorization grâce à req.headers.authorization.

Le frontend doit normalement envoyer une information de ce type :

Authorization: Bearer TOKEN_JWT

Si aucun header Authorization n'est envoyé, le serveur retourne une erreur HTTP 401 avec le message "No token provided".

Ensuite, le serveur vérifie que le header commence bien par Bearer . Cela permet de s'assurer que le format du token est correct.

Le token est ensuite récupéré avec : authHeader.split(" ")[1].

La fonction jwt.verify() vérifie ensuite le token avec la clé secrète contenue dans la variable d'environnement JWT_SECRET.

Si le token est valide, les informations contenues dans le token sont placées dans req.user.

Cela permet aux contrôleurs suivants de connaître l'utilisateur connecté.

Enfin, next() permet de continuer vers le middleware ou le contrôleur suivant.

3. Gestion des erreurs JWT

Si le token est incorrect, expiré ou invalide, une exception est générée. Le bloc catch récupère cette erreur.

Le serveur retourne alors une réponse HTTP 401 avec le message Invalid token.

4. Middleware isAdmin

Le middleware isAdmin permet de vérifier que l'utilisateur connecté possède le rôle admin.

La condition vérifie :

req.user && req.user.role === "admin"

Si l'utilisateur est bien administrateur, next() permet d'accéder au contrôleur.

Sinon, le serveur retourne une erreur HTTP 403. Cela signifie que l'utilisateur est authentifié mais qu'il n'a pas les droits nécessaires.

5. Deuxième version de isAdmin

Dans ton code, il existe également une deuxième fonction appelée isAdmin. Elle vérifie directement :

req.user.role !== "admin"

Si le rôle n'est pas admin, elle retourne une erreur 403. Sinon, elle appelle next().

Il est préférable de garder une seule version de isAdmin pour éviter les doublons et les conflits d'importation.

6. Middleware Multer

Le middleware Multer permet de gérer l'envoi de fichiers depuis le frontend vers le serveur, notamment les images des produits.

multer.diskStorage() définit la manière dont les fichiers seront stockés sur le serveur.

La propriété destination indique que les fichiers seront enregistrés dans le dossier :

uploads/

La propriété filename permet de générer un nom unique pour chaque image.

Le nom contient la date actuelle grâce à Date.now(), suivie du nom original du fichier.

Par exemple, une image appelée vitamine.jpg peut devenir :

1725647890000-vitamine.jpg

La fonction multer({ storage }) crée ensuite le middleware d'upload.

7. Routes des commandes

Le fichier de routes des commandes utilise Express pour définir les différentes URL liées aux commandes.

Le router est créé avec :

const router = express.Router();

Les fonctions du contrôleur orderController sont ensuite importées.

8. Création d'une commande

La route :

POST /api/orders

permet de créer une nouvelle commande.

Elle utilise le middleware auth. Cela signifie que seul un utilisateur connecté peut créer une commande.

Le contrôleur appelé est createOrder.

9. Récupération de toutes les commandes

La route :

GET /api/orders

permet de récupérer toutes les commandes.

Elle est protégée par deux middlewares : auth puis isAdmin.

Cela signifie qu'il faut être connecté et avoir le rôle administrateur.

10. Récupération des commandes d'un utilisateur

La route :

GET /api/orders/user/:userId

permet de récupérer les commandes associées à un utilisateur donné.

La route est protégée par auth, mais dans cette version le middleware isAdmin n'est pas utilisé.

11. Récupération d'une commande

La route :

GET /api/orders/:id

permet de récupérer une commande grâce à son identifiant MongoDB.

L'utilisateur doit être authentifié grâce au middleware auth.

12. Modification du statut d'une commande

La route :

PUT /api/orders/:id/status

permet de modifier le statut d'une commande.

Elle est réservée aux administrateurs.

Le statut peut par exemple passer de En attente à En préparation, puis à Expédiée et enfin Livrée.

13. Modification du statut de paiement

La route :

PUT /api/orders/:id/payment-status

permet de modifier le statut du paiement d'une commande.

Cette opération est également réservée à l'administrateur.

14. Suppression d'une commande

La route :

DELETE /api/orders/:id

permet de supprimer une commande.

Cette opération est protégée par auth et isAdmin. Un utilisateur normal ne peut donc pas supprimer une commande.

15. Routes des paiements Stripe

Le fichier paymentRoutes.js contient les routes permettant de gérer les paiements avec Stripe.

16. Création d'une session Stripe

La route :

POST /api/payments/create-checkout-session

permet de créer une session de paiement Stripe.

La route utilise le middleware auth. L'utilisateur doit donc être connecté avant de pouvoir effectuer le paiement.

Le contrôleur appelé est createCheckoutSession.

17. Récupération des paiements

La route :

GET /api/payments/admin

permet à l'administrateur de récupérer la liste des paiements.

Elle utilise auth et isAdmin.

18. Webhook Stripe

La route :

POST /api/payments/webhook

est utilisée par Stripe pour envoyer automatiquement des notifications au serveur.

Elle utilise express.raw() parce que Stripe a besoin du contenu brut de la requête pour vérifier la signature du webhook.

Le contrôleur stripeWebhook reçoit ensuite l'événement envoyé par Stripe.

19. Routes des produits

Le fichier productRoutes.js contient les routes permettant de gérer les produits de la pharmacie.

20. Création d'un produit

La route :

POST /api/products

permet à un administrateur de créer un nouveau produit.

Elle utilise trois middlewares : auth, isAdmin et upload.single("image").

Le premier vérifie l'identité de l'utilisateur. Le deuxième vérifie qu'il est administrateur. Le troisième permet de recevoir une image.

21. Récupération des produits

La route :

GET /api/products

permet de récupérer tous les produits.

Cette route est publique. Aucun token JWT n'est nécessaire.

Cela permet aux visiteurs et aux clients de consulter les produits disponibles.

22. Modification d'un produit

La route :

PUT /api/products/:id

permet à un administrateur de modifier un produit.

L'image est optionnelle grâce à upload.single("image").

Si une nouvelle image est envoyée, elle peut remplacer l'ancienne image.

23. Routes des ventes

Le fichier salesRoutes.js permet d'accéder aux statistiques commerciales de la plateforme.

24. Vue globale des ventes

La route :

GET /api/sales/overview

permet de récupérer une vue globale des ventes.

Elle est protégée par auth et isAdmin. Seul un administrateur peut consulter ces informations.

Le contrôleur peut retourner notamment le chiffre d'affaires total, le nombre de commandes et la moyenne des commandes.

25. Ventes par jour

La route :

GET /api/sales/by-day

permet d'obtenir les ventes regroupées par jour.

Ces données peuvent ensuite être utilisées dans un dashboard administrateur pour afficher des graphiques statistiques.

26. Routes des paramètres

Le fichier settingsRoutes.js permet de gérer les paramètres généraux de la boutique.

27. Récupération des paramètres

La route :

GET /api/settings

permet à l'administrateur de récupérer les paramètres de la boutique.

Elle nécessite une authentification et le rôle administrateur.

28. Modification des paramètres

La route :

PUT /api/settings

permet à l'administrateur de modifier les paramètres.

Ces paramètres peuvent concerner le nom de la boutique, l'email, le téléphone, l'adresse, la devise, les commandes, la maintenance, la livraison et Stripe.

29. Routes utilisateurs

Le fichier userRoutes.js contient les routes liées à l'authentification et aux clients.

30. Inscription

La route :

POST /api/users/register

permet à un nouvel utilisateur de créer un compte.

Cette route est publique car l'utilisateur n'est pas encore connecté.

31. Connexion

La route :

POST /api/users/login

permet à un utilisateur existant de se connecter.

Le serveur vérifie l'adresse email et le mot de passe. Si les informations sont correctes, un token JWT est généré.

32. Liste des clients

La route :

GET /api/users/customers

permet de récupérer la liste des clients.

Dans le contrôleur, seuls les utilisateurs ayant le rôle user sont sélectionnés.

33. Récupération d'un client

La route :

GET /api/users/customers/:id

permet de récupérer un client grâce à son identifiant.

34. Suppression d'un client

La route :

DELETE /api/users/customers/:id

permet de supprimer un client.

Attention : dans le code présenté, ces trois routes clients ne sont pas protégées par auth et isAdmin.

Pour une application réelle, il est fortement recommandé de protéger ces routes si elles sont utilisées uniquement par l'administration.

35. Script Python de lancement du scraper

Le code :

from scrapers.pharma_scraper import scrape_products scrape_products()

importe une fonction appelée scrape_products depuis le module scrapers.pharma_scraper.

Ensuite, la fonction est exécutée avec scrape_products().

Son objectif est de lancer automatiquement le scraping des produits.

36. Bibliothèque Requests

Dans le scraper Python, la bibliothèque requests permet d'envoyer une requête HTTP vers un site web.

La fonction requests.get() récupère le contenu HTML de la page.

37. Bibliothèque BeautifulSoup

BeautifulSoup permet d'analyser le code HTML récupéré depuis le site web.

Grâce à BeautifulSoup, le programme peut rechercher les éléments HTML contenant les informations des produits.

38. Connexion à MongoDB avec Python

La bibliothèque pymongo permet à Python de communiquer avec MongoDB.

La connexion est réalisée avec :

MongoClient("mongodb://localhost:27017/")

Le programme se connecte donc à une instance MongoDB installée localement sur la machine.

39. Base de données pharma_db

Le code utilise la base de données :

pharma_db

Puis il utilise la collection :

products

Les produits récupérés depuis les sites web seront enregistrés dans cette collection.

40. Premier scraper : Pharma Shop

Le premier scraper utilise l'adresse :

https://pharma-shop.tn/

Le programme envoie une requête HTTP avec un User-Agent. Cela permet de simuler un navigateur lors de la récupération de la page.

41. Recherche des produits

Le programme recherche tous les éléments HTML ayant la structure :

div class="product"

Chaque élément trouvé est considéré comme un produit.

42. Extraction du nom du produit

Pour chaque produit, le programme recherche la balise h2.

Le texte est ensuite récupéré avec .text et nettoyé avec .strip().

Le résultat est enregistré dans la variable name.

43. Extraction du prix

Le scraper recherche ensuite une balise :

span class="price"

Le contenu de cette balise est récupéré et enregistré dans la variable price.

44. Création de l'objet produit

Le programme crée ensuite un dictionnaire Python contenant le nom et le prix :

{ "name": name, "price": price }

Cet objet représente les informations du produit qui seront enregistrées dans MongoDB.

45. Insertion dans MongoDB

La fonction collection.insert_one() permet d'insérer un produit dans MongoDB.

Après l'insertion, le programme affiche le nom du produit dans la console grâce à print("Inserted:", name).

46. Gestion des erreurs du scraper

Le traitement de chaque produit est placé dans un bloc try / except.

Si le scraper rencontre un problème pour récupérer le nom, le prix ou insérer le produit, l'erreur est capturée et affichée dans la console.

Cela permet au scraper de continuer son traitement au lieu de s'arrêter complètement à la première erreur.

47. Deuxième scraper : Doppelherz

Le deuxième scraper fonctionne de manière similaire, mais il utilise une autre source :

https://www.doppelherz.tn/produits

Il récupère le contenu de cette page avec requests.

Ensuite, BeautifulSoup analyse le HTML et recherche les éléments ayant la classe product.

Pour chaque produit, le programme récupère son nom et son prix.

Les informations sont ensuite enregistrées dans la même collection MongoDB : pharma_db.products.

48. Exécution directe du scraper

La condition :

if __name__ == "__main__":

permet d'exécuter automatiquement la fonction scrape_and_save() lorsque le fichier Python est lancé directement.

Cela évite que la fonction soit automatiquement exécutée si le fichier est simplement importé dans un autre programme.

49. Architecture générale du projet

L'architecture globale peut être représentée de la manière suivante :

Frontend React ↓ API REST Express ↓ Middleware JWT ↓ Routes ↓ Controllers ↓ Models Mongoose ↓ MongoDB

Pour les paiements, une partie supplémentaire intervient :

React ↓ Express ↓ Payment Controller ↓ Stripe Checkout ↓ Stripe Webhook ↓ MongoDB

Pour la récupération des produits externes, le flux est différent :

Site externe ↓ Python Requests ↓ BeautifulSoup ↓ Scraper ↓ PyMongo ↓ MongoDB

50. Flux d'authentification

Lorsqu'un utilisateur s'inscrit, le serveur crée son compte et génère un token JWT.

Lorsqu'il se connecte, le serveur vérifie son mot de passe puis génère également un token JWT.

Le frontend conserve ensuite ce token et l'envoie dans les requêtes nécessitant une authentification.

Le middleware auth vérifie le token et place les informations de l'utilisateur dans req.user.

Le middleware isAdmin vérifie ensuite le rôle de cet utilisateur.

51. Flux d'une commande

Le client consulte les produits grâce à la route publique GET /api/products.

Il ajoute ensuite les produits au panier.

Lorsqu'il valide son panier, le frontend envoie une requête POST /api/orders.

Le middleware JWT vérifie que le client est connecté.

Le contrôleur createOrder valide les produits, calcule le montant total et crée la commande dans MongoDB.

52. Flux du paiement Stripe

Après la création de la commande, le frontend peut demander la création d'une session Stripe.

Le backend vérifie que la commande appartient bien à l'utilisateur connecté.

Il crée ensuite une session Stripe Checkout contenant les produits et leurs prix.

Le client est redirigé vers Stripe pour effectuer le paiement.

Une fois le paiement terminé, Stripe peut envoyer un événement au serveur grâce au webhook.

Le webhook met alors à jour le paiement et la commande dans MongoDB.

53. Flux du scraping

Les scripts Python permettent de récupérer automatiquement des produits depuis plusieurs sites pharmaceutiques.

Le scraper envoie une requête HTTP, analyse la page HTML, récupère les informations des produits puis les sauvegarde dans MongoDB.

Les données peuvent ensuite être récupérées par le backend Node.js et affichées dans l'application React.

54. Points importants à améliorer

Le premier point concerne les doublons de code. Tu as deux versions du middleware isAdmin. Il est préférable de conserver une seule fonction isAdmin.

Le deuxième point concerne les routes clients. Les routes /customers sont actuellement publiques. Si elles sont destinées au dashboard administrateur, il est préférable d'utiliser :

auth, isAdmin

avant les contrôleurs concernés.

Le troisième point concerne le scraping. Les sélecteurs HTML div.product, h2 et span.price doivent correspondre exactement à la structure réelle des sites concernés. Si le site change son HTML, le scraper peut ne plus fonctionner.

Le quatrième point concerne le prix. Dans le scraper, le prix est actuellement récupéré comme une chaîne de caractères. Pour effectuer correctement des calculs dans MongoDB ou dans le backend, il est préférable de nettoyer puis convertir le prix en nombre.

Le cinquième point concerne les variables sensibles. Les valeurs comme JWT_SECRET et STRIPE_SECRET_KEY doivent être conservées dans le fichier .env et ne doivent jamais être publiées sur GitHub.

55. Résumé général

Le backend de cette plateforme Pharma est construit autour de plusieurs technologies complémentaires.

Node.js et Express permettent de créer l'API REST et les routes.

JWT permet d'authentifier les utilisateurs et de protéger les routes privées.

isAdmin permet de limiter certaines fonctionnalités aux administrateurs.

Multer permet de recevoir et stocker les images des produits.

MongoDB permet de stocker les utilisateurs, produits, commandes, paiements et paramètres.

Stripe permet de gérer les paiements en ligne.

Python Requests et BeautifulSoup permettent de récupérer les produits depuis des sites externes.

PyMongo permet ensuite au scraper Python d'enregistrer les produits récupérés directement dans MongoDB.

L'ensemble forme donc une architecture complète de commerce électronique avec gestion des utilisateurs, administration, produits, commandes, paiements, statistiques et récupération automatisée de données externes.
