Explicação do Backend da Plataforma Pharma

1. Middleware de autenticação JWT

O middleware de autenticação protege as rotas da aplicação. Ele verifica se o usuário possui um token JWT válido antes de permitir o acesso a determinadas funcionalidades.

O módulo jsonwebtoken é importado por meio de require("jsonwebtoken"). Ele é utilizado para verificar os tokens JWT enviados pelo frontend.

2. Função auth

A função auth é um middleware executado antes de determinados controladores. Sua função é verificar a identidade do usuário.

O middleware obtém o cabeçalho HTTP Authorization por meio de req.headers.authorization.

Normalmente, o frontend deve enviar a informação neste formato:

Authorization: Bearer TOKEN_JWT

Se nenhum cabeçalho Authorization for enviado, o servidor retorna um erro HTTP 401 com a mensagem "No token provided".

Em seguida, o servidor verifica se o cabeçalho começa corretamente com Bearer . Isso permite verificar se o formato do token está correto.

O token é obtido por meio de: authHeader.split(" ")[1].

A função jwt.verify() verifica então o token utilizando a chave secreta armazenada na variável de ambiente JWT_SECRET.

Se o token for válido, as informações contidas no token são armazenadas em req.user.

Isso permite que os próximos controladores saibam qual usuário está conectado.

Por fim, next() permite continuar para o próximo middleware ou controlador.

3. Tratamento de erros JWT

Se o token estiver incorreto, expirado ou inválido, uma exceção será gerada. O bloco catch captura esse erro.

O servidor retorna então uma resposta HTTP 401 com a mensagem Invalid token.

4. Middleware isAdmin

O middleware isAdmin verifica se o usuário conectado possui a função admin.

A condição verifica:

req.user && req.user.role === "admin"

Se o usuário for administrador, next() permite o acesso ao controlador.

Caso contrário, o servidor retorna um erro HTTP 403. Isso significa que o usuário está autenticado, mas não possui as permissões necessárias.

5. Segunda versão de isAdmin

No seu código também existe uma segunda função chamada isAdmin. Ela verifica diretamente:

req.user.role !== "admin"

Se a função do usuário não for admin, retorna um erro 403. Caso contrário, chama next().

É preferível manter apenas uma versão de isAdmin para evitar duplicações e conflitos de importação.

6. Middleware Multer

O middleware Multer permite gerenciar o upload de arquivos do frontend para o servidor, especialmente as imagens dos produtos.

multer.diskStorage() define como os arquivos serão armazenados no servidor.

A propriedade destination indica que os arquivos serão salvos na pasta:

uploads/

A propriedade filename permite gerar um nome único para cada imagem.

O nome contém a data atual por meio de Date.now(), seguida pelo nome original do arquivo.

Por exemplo, uma imagem chamada vitamine.jpg pode se tornar:

1725647890000-vitamine.jpg

A função multer({ storage }) cria então o middleware de upload de arquivos.

7. Rotas de pedidos

O arquivo de rotas de pedidos utiliza Express para definir as diferentes URLs relacionadas aos pedidos.

O router é criado por meio de:

const router = express.Router();

Em seguida, as funções do orderController são importadas.

8. Criação de um pedido

A rota:

POST /api/orders

permite criar um novo pedido.

Ela utiliza o middleware auth. Isso significa que somente um usuário conectado pode criar um pedido.

O controlador utilizado é createOrder.

9. Recuperação de todos os pedidos

A rota:

GET /api/orders

permite recuperar todos os pedidos.

Ela é protegida por dois middlewares: auth seguido de isAdmin.

Isso significa que o usuário deve estar conectado e possuir a função de administrador.

10. Recuperação dos pedidos de um usuário

A rota:

GET /api/orders/user/:userId

permite recuperar os pedidos associados a um usuário específico.

A rota é protegida por auth, mas nesta versão o middleware isAdmin não é utilizado.

11. Recuperação de um pedido

A rota:

GET /api/orders/:id

permite recuperar um pedido utilizando seu identificador do MongoDB.

O usuário deve estar autenticado por meio do middleware auth.

12. Atualização do status de um pedido

A rota:

PUT /api/orders/:id/status

permite modificar o status de um pedido.

Ela é reservada aos administradores.

O status pode, por exemplo, passar de En attente para En préparation, depois para Expédiée e finalmente para Livrée.

13. Atualização do status do pagamento

A rota:

PUT /api/orders/:id/payment-status

permite modificar o status do pagamento de um pedido.

Essa operação também é reservada ao administrador.

14. Exclusão de um pedido

A rota:

DELETE /api/orders/:id

permite excluir um pedido.

Essa operação é protegida por auth e isAdmin. Portanto, um usuário comum não pode excluir um pedido.

15. Rotas de pagamento do Stripe

O arquivo paymentRoutes.js contém as rotas utilizadas para gerenciar os pagamentos com Stripe.

16. Criação de uma sessão do Stripe

A rota:

POST /api/payments/create-checkout-session

permite criar uma sessão de pagamento do Stripe.

A rota utiliza o middleware auth. Portanto, o usuário deve estar conectado antes de realizar o pagamento.

O controlador utilizado é createCheckoutSession.

17. Recuperação dos pagamentos

A rota:

GET /api/payments/admin

permite que o administrador recupere a lista de pagamentos.

Ela utiliza auth e isAdmin.

18. Webhook do Stripe

A rota:

POST /api/payments/webhook

é utilizada pelo Stripe para enviar automaticamente notificações ao servidor.

Ela utiliza express.raw() porque o Stripe precisa do corpo original da solicitação para verificar a assinatura do webhook.

O controlador stripeWebhook recebe então o evento enviado pelo Stripe.

19. Rotas de produtos

O arquivo productRoutes.js contém as rotas utilizadas para gerenciar os produtos da farmácia.

20. Criação de um produto

A rota:

POST /api/products

permite que um administrador crie um novo produto.

Ela utiliza três middlewares: auth, isAdmin e upload.single("image").

O primeiro verifica a identidade do usuário. O segundo verifica se ele é administrador. O terceiro permite receber uma imagem.

21. Recuperação dos produtos

A rota:

GET /api/products

permite recuperar todos os produtos.

Essa rota é pública. Nenhum token JWT é necessário.

Isso permite que visitantes e clientes consultem os produtos disponíveis.

22. Modificação de um produto

A rota:

PUT /api/products/:id

permite que um administrador modifique um produto.

A imagem é opcional graças a upload.single("image").

Se uma nova imagem for enviada, ela poderá substituir a imagem anterior.

23. Rotas de vendas

O arquivo salesRoutes.js permite acessar as estatísticas de vendas da plataforma.

24. Visão geral das vendas

A rota:

GET /api/sales/overview

permite obter uma visão geral das vendas.

Ela é protegida por auth e isAdmin. Somente um administrador pode consultar essas informações.

O controlador pode retornar, entre outros dados, a receita total, o número de pedidos e o valor médio dos pedidos.

25. Vendas por dia

A rota:

GET /api/sales/by-day

permite obter as vendas agrupadas por dia.

Esses dados podem ser utilizados posteriormente em um dashboard de administração para exibir gráficos estatísticos.

26. Rotas de configuração

O arquivo settingsRoutes.js permite gerenciar os parâmetros gerais da loja.

27. Recuperação das configurações

A rota:

GET /api/settings

permite que o administrador recupere as configurações da loja.

É necessário possuir autenticação e a função de administrador.

28. Modificação das configurações

A rota:

PUT /api/settings

permite que o administrador modifique as configurações.

Esses parâmetros podem incluir o nome da loja, o email, o telefone, o endereço, a moeda, os pedidos, a manutenção, a entrega e o Stripe.

29. Rotas de usuários

O arquivo userRoutes.js contém as rotas relacionadas à autenticação e aos clientes.

30. Registro

A rota:

POST /api/users/register

permite que um novo usuário crie uma conta.

Essa rota é pública porque o usuário ainda não iniciou sessão.

31. Login

A rota:

POST /api/users/login

permite que um usuário existente faça login.

O servidor verifica o endereço de email e a senha. Se as informações estiverem corretas, um token JWT será gerado.

32. Lista de clientes

A rota:

GET /api/users/customers

permite recuperar a lista de clientes.

No controlador, são selecionados apenas os usuários que possuem a função user.

33. Recuperação de um cliente

A rota:

GET /api/users/customers/:id

permite recuperar um cliente utilizando seu identificador.

34. Exclusão de um cliente

A rota:

DELETE /api/users/customers/:id

permite excluir um cliente.

Atenção: no código apresentado, essas três rotas de clientes não estão protegidas por auth e isAdmin.

Para uma aplicação real, é altamente recomendável proteger essas rotas caso sejam destinadas a ser utilizadas exclusivamente pela administração.

35. Script de execução do scraper Python

O código:

from scrapers.pharma_scraper import scrape_products scrape_products()

importa uma função chamada scrape_products do módulo scrapers.pharma_scraper.

Em seguida, a função é executada por meio de scrape_products().

Seu objetivo é iniciar automaticamente o scraping dos produtos.

36. Biblioteca Requests

No scraper Python, a biblioteca requests é utilizada para enviar uma solicitação HTTP a um site.

A função requests.get() recupera o conteúdo HTML da página.

37. Biblioteca BeautifulSoup

BeautifulSoup é utilizada para analisar o código HTML recuperado do site.

Graças ao BeautifulSoup, o programa pode pesquisar elementos HTML que contêm informações sobre os produtos.

38. Conexão ao MongoDB com Python

A biblioteca pymongo permite que o Python se comunique com o MongoDB.

A conexão é realizada por meio de:

MongoClient("mongodb://localhost:27017/")

Portanto, o programa se conecta a uma instância do MongoDB instalada localmente na máquina.

39. Banco de dados pharma_db

O código utiliza o banco de dados:

pharma_db

Em seguida, utiliza a coleção:

products

Os produtos recuperados dos sites serão armazenados nessa coleção.

40. Primeiro scraper: Pharma Shop

O primeiro scraper utiliza o endereço:

[https://pharma-shop.tn/](https://pharma-shop.tn/)

O programa envia uma solicitação HTTP com um User-Agent. Isso permite simular um navegador ao recuperar a página.

41. Busca de produtos

O programa procura todos os elementos HTML com a seguinte estrutura:

div class="product"

Cada elemento encontrado é considerado um produto.

42. Extração do nome do produto

Para cada produto, o programa procura a tag h2.

Em seguida, o texto é obtido por meio de .text e limpo por meio de .strip().

O resultado é armazenado na variável name.

43. Extração do preço

O scraper procura então uma tag:

span class="price"

O conteúdo dessa tag é recuperado e armazenado na variável price.

44. Criação do objeto produto

O programa cria então um dicionário Python contendo o nome e o preço:

{ "name": name, "price": price }

Esse objeto representa as informações do produto que serão armazenadas no MongoDB.

45. Inserção no MongoDB

A função collection.insert_one() é utilizada para inserir um produto no MongoDB.

Após a inserção, o programa exibe o nome do produto no console por meio de print("Inserted:", name).

46. Tratamento de erros do scraper

O processamento de cada produto é colocado dentro de um bloco try / except.

Se o scraper encontrar um problema ao recuperar o nome, o preço ou inserir o produto, o erro será capturado e exibido no console.

Isso permite que o scraper continue processando em vez de parar completamente ao encontrar o primeiro erro.

47. Segundo scraper: Doppelherz

O segundo scraper funciona de maneira semelhante, mas utiliza outra fonte:

[https://www.doppelherz.tn/produits](https://www.doppelherz.tn/produits)

Ele recupera o conteúdo dessa página utilizando requests.

Em seguida, BeautifulSoup analisa o HTML e procura elementos que possuem a classe product.

Para cada produto, o programa recupera seu nome e seu preço.

As informações são posteriormente armazenadas na mesma coleção do MongoDB: pharma_db.products.

48. Execução direta do scraper

A condição:

if __name__ == "__main__":

permite executar automaticamente a função scrape_and_save() quando o arquivo Python é executado diretamente.

Isso evita que a função seja executada automaticamente quando o arquivo é simplesmente importado em outro programa.

49. Arquitetura geral do projeto

A arquitetura geral pode ser representada da seguinte forma:

React Frontend ↓ Express REST API ↓ JWT Middleware ↓ Routes ↓ Controllers ↓ Mongoose Models ↓ MongoDB

Para os pagamentos, existe uma parte adicional:

React ↓ Express ↓ Payment Controller ↓ Stripe Checkout ↓ Stripe Webhook ↓ MongoDB

Para a recuperação de produtos externos, o fluxo é diferente:

External Website ↓ Python Requests ↓ BeautifulSoup ↓ Scraper ↓ PyMongo ↓ MongoDB

50. Fluxo de autenticação

Quando um usuário se registra, o servidor cria sua conta e gera um token JWT.

Quando o usuário faz login, o servidor verifica sua senha e também gera um token JWT.

O frontend armazena então esse token e o envia com as solicitações que exigem autenticação.

O middleware auth verifica o token e coloca as informações do usuário em req.user.

Em seguida, o middleware isAdmin verifica a função do usuário.

51. Fluxo de um pedido

O cliente consulta os produtos por meio da rota pública GET /api/products.

Em seguida, adiciona os produtos ao carrinho.

Quando confirma o carrinho, o frontend envia uma solicitação POST /api/orders.

O middleware JWT verifica se o cliente está conectado.

O controlador createOrder valida os produtos, calcula o valor total e cria o pedido no MongoDB.

52. Fluxo de pagamento com Stripe

Depois de criar o pedido, o frontend pode solicitar a criação de uma sessão do Stripe.

O backend verifica se o pedido pertence ao usuário conectado.

Em seguida, cria uma sessão do Stripe Checkout contendo os produtos e seus preços.

O cliente é redirecionado para o Stripe para realizar o pagamento.

Depois que o pagamento é concluído, o Stripe pode enviar um evento ao servidor por meio do webhook.

O webhook atualiza então o pagamento e o pedido no MongoDB.

53. Fluxo de scraping

Os scripts Python permitem recuperar automaticamente produtos de vários sites farmacêuticos.

O scraper envia uma solicitação HTTP, analisa a página HTML, recupera as informações dos produtos e posteriormente as salva no MongoDB.

Os dados podem ser recuperados posteriormente pelo backend Node.js e exibidos na aplicação React.

54. Pontos importantes a melhorar

O primeiro ponto refere-se ao código duplicado. Você possui duas versões do middleware isAdmin. É preferível manter apenas uma função isAdmin.

O segundo ponto refere-se às rotas de clientes. As rotas /customers atualmente são públicas. Se forem destinadas ao dashboard de administração, é preferível utilizar:

auth, isAdmin

antes dos controladores correspondentes.

O terceiro ponto refere-se ao scraping. Os seletores HTML div.product, h2 e span.price devem corresponder exatamente à estrutura real dos sites correspondentes. Se o site alterar seu HTML, o scraper poderá deixar de funcionar.

O quarto ponto refere-se ao preço. No scraper, o preço atualmente é recuperado como uma string de caracteres. Para realizar corretamente cálculos no MongoDB ou no backend, é preferível limpar o preço e depois convertê-lo em um número.

O quinto ponto refere-se às variáveis sensíveis. Valores como JWT_SECRET e STRIPE_SECRET_KEY devem ser armazenados no arquivo .env e nunca devem ser publicados no GitHub.

55. Resumo geral

O backend desta plataforma Pharma é construído em torno de várias tecnologias complementares.

Node.js e Express permitem criar a API REST e as rotas.

JWT permite autenticar os usuários e proteger as rotas privadas.

isAdmin permite restringir determinadas funcionalidades aos administradores.

Multer permite receber e armazenar as imagens dos produtos.

MongoDB permite armazenar usuários, produtos, pedidos, pagamentos e configurações.

Stripe permite gerenciar os pagamentos online.

Python Requests e BeautifulSoup permitem recuperar produtos de sites externos.

PyMongo permite posteriormente que o scraper Python salve os produtos recuperados diretamente no MongoDB.

Todo o sistema forma, portanto, uma arquitetura completa de comércio eletrônico com gerenciamento de usuários, administração, produtos, pedidos, pagamentos, estatísticas e recuperação automatizada de dados externos.
