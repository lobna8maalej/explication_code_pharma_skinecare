Documentation de l'administration de la boutique

Cette documentation explique en détail le fonctionnement des composants React utilisés dans l'espace d'administration de la boutique.

Les composants étudiés sont AdminOrders, AdminProducts et AdminPayments.

Ces composants permettent à l'administrateur de gérer les commandes, les produits, le stock et les paiements effectués avec Stripe.

1. Architecture générale

L'application utilise React pour construire l'interface utilisateur de l'administration. React communique avec le backend grâce à la bibliothèque Axios.

Le frontend envoie des requêtes HTTP vers l'API backend disponible ici : http://localhost:3000/api.

Le backend reçoit les requêtes, exécute les traitements nécessaires, communique avec MongoDB et retourne les résultats au frontend.

React Admin → Axios → API Express/Node.js → MongoDB

Pour certaines opérations administratives, un token JWT est récupéré depuis localStorage puis envoyé dans l'en-tête HTTP Authorization.

2. Composant AdminOrders

Le composant AdminOrders représente la page d'administration consacrée à la gestion des commandes clients.

L'administrateur peut consulter les commandes, voir les informations du client, consulter les produits commandés, connaître le montant total, consulter le paiement, modifier le statut de la commande et supprimer une commande.

3. Importation des dépendances dans AdminOrders

Le composant commence par importer les hooks React useEffect et useState.

useState permet de gérer les données dynamiques de la page, tandis que useEffect permet d'exécuter du code lorsque le composant est chargé.

Axios est utilisé pour communiquer avec le backend.

Le composant importe également AdminNavbar afin d'afficher la barre de navigation de l'administration.

Le fichier AdminOrders.css contient les styles spécifiques à la page des commandes.

4. API utilisée par AdminOrders

La constante API contient l'adresse principale du backend. 

const API = "http://localhost:3000/api";

Toutes les requêtes de commandes sont ensuite construites à partir de cette adresse.

5. État des commandes

Le composant utilise trois états principaux : orders, loading et error.

orders contient la liste des commandes récupérées depuis le backend.

loading indique si les commandes sont actuellement en cours de chargement.

error contient éventuellement le message d'erreur à afficher lorsque la récupération des commandes échoue.

6. Récupération des commandes

La fonction fetchOrders permet de récupérer toutes les commandes depuis l'API.

Avant d'effectuer la requête, le composant récupère le token administrateur enregistré dans localStorage. 

const token = localStorage.getItem("token");

Le token est envoyé au backend avec l'en-tête : Authorization: Bearer token.

Cette méthode permet au backend de vérifier que la requête provient d'un utilisateur authentifié.

7. Requête GET des commandes

La requête suivante permet de demander toutes les commandes : 

axios.get(`${API}/orders`, {
  headers: {
    Authorization: `Bearer ${token}`,
  },
});

Le backend doit alors retourner les commandes dans la propriété orders ou éventuellement dans data.

Le frontend vérifie ensuite que le résultat est bien un tableau avant de l'enregistrer dans orders.

8. useEffect dans AdminOrders

Le hook useEffect est utilisé avec un tableau de dépendances vide. 

useEffect(() => {
  fetchOrders();
}, []);

Cela signifie que fetchOrders est exécutée une seule fois lorsque la page est chargée.

9. Modification du statut d'une commande

La fonction updateStatus permet à l'administrateur de modifier le statut d'une commande.

L'identifiant de la commande ainsi que le nouveau statut sont transmis au backend. 

axios.put(
  `${API}/orders/${orderId}/status`,
  {
    orderStatus: newStatus,
  },
  {
    headers: {
      Authorization: `Bearer ${token}`,
    },
  }
);

Le nouveau statut peut être par exemple : En attente, En préparation, Expédiée, Livrée ou Annulée.

10. Mise à jour immédiate de l'interface

Après la modification réussie du statut, le frontend ne recharge pas nécessairement toute la liste depuis le serveur.

Il modifie directement la commande concernée dans le state orders.

Cette technique permet d'obtenir une interface plus rapide et plus réactive.

11. Suppression d'une commande

La fonction deleteOrder permet de supprimer une commande.

Avant la suppression, une fenêtre de confirmation est affichée avec window.confirm.

Si l'administrateur confirme, une requête HTTP DELETE est envoyée au backend. 

axios.delete(`${API}/orders/${orderId}`, {
  headers: {
    Authorization: `Bearer ${token}`,
  },
});

Après la suppression, la commande est également retirée du state orders.

12. Récupération du nom du client

La fonction getCustomerName permet de déterminer le nom du client associé à une commande.

Le composant vérifie d'abord les informations présentes dans order.customer.

Si le prénom ou le nom existe, ils sont combinés afin de former le nom complet.

Si ces informations ne sont pas disponibles, le composant utilise order.user.username.

Si aucune information n'est disponible, le texte Client inconnu est affiché.

13. Récupération de l'email du client

La fonction getCustomerEmail cherche l'email dans order.customer.email.

Si cette valeur n'existe pas, elle utilise order.user.email.

Si aucune adresse n'est disponible, le texte Email inconnu est affiché.

14. Récupération des produits d'une commande

La fonction getItems vérifie si la commande contient un tableau items.

Si ce tableau n'existe pas, elle vérifie également la propriété products.

Cette logique rend le composant plus flexible lorsqu'une structure différente est retournée par le backend.

15. Calcul du montant total

La fonction getTotal récupère le montant total de la commande.

Elle utilise d'abord totalAmount.

Si cette propriété n'existe pas, elle utilise totalPrice.

Si aucune valeur n'est disponible, le montant par défaut est 0.

16. Statut du paiement

La fonction getPaymentStatus récupère le statut du paiement.

Si aucun statut n'est présent, la valeur par défaut est En attente.

Cela permet d'éviter d'afficher une valeur vide dans l'interface.

17. Statut de la commande

La fonction getOrderStatus récupère le statut actuel de la commande.

Si le backend ne fournit pas de statut, la valeur En attente est utilisée.

18. Formatage des dates

La fonction formatDate transforme une date provenant de MongoDB en une date lisible par l'utilisateur.

Le format utilisé est français grâce à toLocaleDateString("fr-FR").

Une date peut ainsi être affichée sous la forme 07/09/2026.

19. Gestion du chargement

Lorsque loading vaut true, le composant affiche un message indiquant que les commandes sont en cours de chargement.

La barre de navigation AdminNavbar reste également visible.

20. Gestion des erreurs

Si une erreur survient pendant la récupération des commandes, le message est enregistré dans error.

L'utilisateur voit alors un message d'erreur ainsi qu'un bouton Réessayer.

Le bouton permet de relancer la fonction fetchOrders sans devoir recharger manuellement la page.

21. Affichage d'une commande

Chaque commande est affichée sous forme de carte avec la classe order-card.

La carte contient plusieurs informations : numéro de commande, date, client, email, téléphone, adresse, produits, montant, paiement et statut.

22. Affichage des produits

Pour chaque produit commandé, le composant récupère le nom, le prix et la quantité.

Le sous-total est ensuite calculé avec la formule : 

Sous-total = Prix × Quantité

Le résultat est affiché avec deux chiffres après la virgule.

23. Modification du statut avec un select

L'administrateur dispose d'un élément HTML select permettant de choisir le nouveau statut.

Lorsque la valeur change, la fonction updateStatus est automatiquement appelée.

Cela permet de modifier rapidement l'état d'une commande directement depuis le tableau de gestion.

24. Composant AdminProducts

Le composant AdminProducts permet à l'administrateur de gérer les produits de la boutique.

Il permet de consulter les produits, modifier leurs informations, augmenter ou diminuer le stock et supprimer un produit.

25. État des produits

Le state products contient la liste des produits.

Le state loading permet de savoir si les produits sont encore en cours de récupération.

Le state editingProduct contient le produit actuellement sélectionné pour modification.

26. États du formulaire de modification

Plusieurs états sont utilisés pour gérer les champs du formulaire : name, price, stock et category.

Chaque champ est contrôlé par React. Lorsque l'utilisateur écrit dans un champ, son state correspondant est automatiquement mis à jour.

27. Récupération des produits

La fonction fetchProducts envoie une requête GET vers /products. 

axios.get(`${API}/products`);

Le composant accepte plusieurs formats possibles de réponse : un tableau directement, products ou data.

28. Modification rapide du stock

La fonction updateStock permet de modifier le stock d'un produit directement depuis la liste.

Avant l'envoi, le composant vérifie que le nouveau stock n'est pas négatif.

Le nouveau stock est ensuite envoyé au backend avec une requête PUT. 

axios.put(
  `${API}/products/${productId}`,
  {
    stock: Number(newStock)
  }
);

29. Protection contre le stock négatif

Le code empêche volontairement la création d'un stock inférieur à zéro.

Lorsque le stock est égal à zéro, le bouton permettant de diminuer le stock est désactivé.

Cette vérification est importante pour garantir la cohérence des données commerciales.

30. Boutons plus et moins du stock

La fonction decreaseStock diminue le stock de une unité.

La fonction increaseStock augmente le stock de une unité.

Les deux fonctions appellent ensuite updateStock pour envoyer la nouvelle valeur au backend.

31. Indicateur du niveau de stock

Le composant utilise trois niveaux de stock.

Lorsque le stock est égal à zéro, l'interface affiche Rupture.

Lorsque le stock est supérieur à zéro mais inférieur ou égal à cinq, l'interface affiche Stock faible.

Lorsque le stock est supérieur à cinq, l'interface affiche En stock.

32. Ouverture du formulaire de modification

La fonction handleEdit est appelée lorsque l'administrateur clique sur le bouton Modifier.

Elle enregistre le produit sélectionné dans editingProduct et copie ses valeurs dans les différents champs du formulaire.

33. Annulation de la modification

La fonction handleCancelEdit ferme le formulaire de modification.

Elle remet également les champs name, price, stock et category à leurs valeurs initiales.

34. Validation du formulaire produit

Avant de modifier un produit, le code vérifie que tous les champs obligatoires sont renseignés.

Le nom ne doit pas être vide, le prix doit être renseigné, le stock doit être renseigné et une catégorie doit être sélectionnée.

Le prix et le stock ne peuvent pas être négatifs.

35. Enregistrement d'un produit modifié

La fonction handleUpdate envoie les nouvelles informations au backend avec une requête PUT. 

axios.put(
  `${API}/products/${editingProduct._id}`,
  {
    name: name.trim(),
    price: Number(price),
    stock: Number(stock),
    category
  }
);

Après la modification, le formulaire est fermé et fetchProducts() est exécutée afin de récupérer les données actualisées.

36. Suppression d'un produit

La fonction handleDelete permet de supprimer un produit.

Une confirmation est demandée à l'administrateur avant l'exécution de la requête DELETE. 

axios.delete(`${API}/products/${productId}`, {
  headers: {
    Authorization: `Bearer ${token}`
  }
});

Une fois la suppression réussie, le produit est retiré du state products.

37. Affichage du tableau des produits

Les produits sont affichés dans un tableau HTML.

Les colonnes principales sont le produit, le prix, le stock, la catégorie et les actions.

Pour chaque produit, React utilise product._id comme clé unique de la ligne.

38. Composant AdminPayments

Le composant AdminPayments est destiné à la gestion des paiements effectués par les clients.

Dans cette application, les paiements sont associés à Stripe.

L'administrateur peut consulter le nombre total de paiements, les paiements réussis, les paiements en attente et les paiements échoués.

39. État des paiements

Le state payments contient la liste des paiements récupérés depuis le backend.

Le state loading indique si les paiements sont en cours de récupération.

Le state error contient le message d'erreur éventuel.

40. Récupération des paiements

La fonction fetchPayments récupère les paiements depuis l'endpoint /payments/admin. 

axios.get(`${API}/payments/admin`, {
  headers: {
    Authorization: `Bearer ${token}`
  }
});

Cette route est destinée à l'administration et nécessite donc un token d'authentification.

41. Vérification du token administrateur

Avant de contacter l'API, le composant vérifie que le token existe dans localStorage.

Si aucun token n'est trouvé, un message indique que le token administrateur est introuvable.

Cette vérification évite d'envoyer une requête inutile vers une route protégée.

42. Statistiques des paiements

Le composant calcule directement plusieurs statistiques à partir du tableau payments.

payments.length représente le nombre total de paiements.

payments.filter(payment => payment.status === "paid").length permet de compter les paiements réussis.

Les paiements dont le statut est pending sont comptabilisés comme paiements en attente.

Les paiements dont le statut est failed sont comptabilisés comme paiements échoués.

43. Affichage du client du paiement

Pour chaque paiement, le composant affiche le nom d'utilisateur provenant de payment.userId.username.

L'adresse email est récupérée depuis payment.userId.email.

Si ces informations ne sont pas disponibles, des valeurs par défaut sont affichées.

44. Association paiement et commande

Chaque paiement peut être associé à une commande grâce à payment.orderId.

Le composant affiche les derniers caractères de l'identifiant MongoDB de la commande.

L'utilisation de slice(-8) permet d'afficher uniquement les huit derniers caractères de l'identifiant afin de rendre l'affichage plus court.

45. Affichage du montant du paiement

Le montant est converti en nombre avec Number().

Ensuite, toFixed(2) permet d'afficher exactement deux chiffres après la virgule.

La devise provenant de payment.currency est convertie en majuscules grâce à toUpperCase().

Par exemple, une devise usd devient USD.

46. Méthode de paiement

Le composant affiche actuellement Stripe comme méthode de paiement.

Un badge visuel avec la classe stripe-badge est utilisé pour distinguer cette méthode.

47. Statut du paiement

Le statut du paiement peut être paid, pending, failed ou refunded.

Le frontend transforme ces valeurs techniques en textes français.

paid devient Payé.

pending devient En attente.

failed devient Échec.

refunded devient Remboursé.

48. Statut de la commande associée

Le composant essaie également d'afficher le statut de la commande associée au paiement.

Cette information est récupérée depuis payment.orderId.status.

Il faut vérifier que le backend utilise réellement le nom status pour le statut de la commande.

Dans le contrôleur des commandes présenté précédemment, le champ utilisé est plutôt orderStatus. Si le backend retourne orderStatus, le frontend devra utiliser payment.orderId.orderStatus.

49. Affichage de la date du paiement

La date est récupérée depuis payment.createdAt.

Elle est convertie au format français avec toLocaleDateString("fr-FR").

50. Bouton Actualiser

Le bouton Actualiser permet à l'administrateur de relancer manuellement la fonction fetchPayments.

Cela permet d'obtenir immédiatement les dernières informations provenant du backend sans recharger toute l'application.

51. Gestion des paiements vides

Lorsque le tableau payments est vide, le composant affiche le message Aucun paiement trouvé..

Le message occupe les sept colonnes du tableau grâce à colSpan="7".

52. Gestion du chargement des paiements

Lorsque les paiements sont encore en cours de chargement, l'utilisateur voit le texte Chargement des paiements....

Cette fonctionnalité évite que l'utilisateur pense que la page est vide alors que les données sont simplement en train d'être récupérées.

53. Gestion des erreurs des paiements

Si la requête échoue, le composant récupère le message fourni par le backend grâce à error.response?.data?.message.

Si aucun message backend n'est disponible, un message générique est affiché.

Le bouton Réessayer permet ensuite de relancer la récupération.

54. Authentification JWT

Les composants administratifs utilisent un token JWT stocké dans localStorage.

Le token est envoyé dans l'en-tête : Authorization: Bearer token.

Le backend peut alors utiliser ce token pour identifier l'utilisateur connecté et contrôler ses permissions.

55. Communication avec MongoDB

Le frontend React ne communique pas directement avec MongoDB.

React envoie une requête HTTP au serveur Node.js/Express.

Le serveur utilise ensuite Mongoose pour communiquer avec MongoDB.

Admin → React → Axios → Express → Controller → Mongoose → MongoDB

56. Cycle de gestion d'une commande

Lorsqu'une commande est créée par un client, elle est enregistrée dans MongoDB.

L'administrateur ouvre ensuite la page AdminOrders.

React demande les commandes au backend.

Le backend récupère les commandes depuis MongoDB et les retourne au frontend.

L'administrateur peut ensuite modifier le statut ou supprimer une commande.

57. Cycle de gestion d'un produit

L'administrateur ouvre AdminProducts.

Le frontend récupère les produits depuis l'API.

L'administrateur peut modifier le nom, le prix, le stock et la catégorie.

Il peut également modifier rapidement le stock avec les boutons + et −.

Toutes les modifications sont ensuite enregistrées dans MongoDB via l'API backend.

58. Cycle de gestion d'un paiement

Lorsqu'un client effectue un paiement avec Stripe, le backend enregistre les informations du paiement.

Le paiement peut ensuite être consulté depuis AdminPayments.

L'administrateur peut voir le client, la commande, le montant, la devise, le statut du paiement et la date.

59. Relation entre commandes et paiements

Une commande possède des informations concernant son paiement, notamment son statut de paiement.

Le paiement possède également une référence vers la commande avec orderId.

Cela permet de relier les deux informations et de suivre le processus complet d'une vente.

60. Relation entre produits et commandes

Une commande contient une liste de produits dans items.

Chaque élément peut contenir un produit, son nom, son prix et sa quantité.

Cela permet à l'administration de savoir exactement quels produits ont été commandés.

61. Rôle de AdminNavbar

Le composant AdminNavbar représente la navigation principale de l'espace administrateur.

Il contient des liens vers le Dashboard, les produits, les commandes, les paiements, les ventes, les paramètres et les clients.

Le composant utilise Link de React Router afin de naviguer entre les différentes pages sans recharger complètement l'application.

62. Déconnexion de l'administrateur

La fonction handleLogout supprime le token et les informations utilisateur stockées dans localStorage. 

localStorage.removeItem("token");
localStorage.removeItem("user");

Ensuite, l'utilisateur est redirigé vers la page /auth.

63. Résumé de AdminOrders

AdminOrders est responsable de la gestion complète des commandes depuis l'espace administrateur.

Il récupère les commandes, affiche les informations du client, affiche les produits, calcule les sous-totaux, affiche les paiements, permet de modifier le statut et permet de supprimer une commande.

64. Résumé de AdminProducts

AdminProducts permet de gérer le catalogue de produits.

Il permet de consulter les produits, modifier leurs informations, contrôler leur stock et supprimer les produits.

65. Résumé de AdminPayments

AdminPayments permet de surveiller les paiements Stripe réalisés par les clients.

Il fournit des statistiques sur les paiements et affiche les informations détaillées de chaque transaction.

67. Points importants à vérifier

Le frontend utilise actuellement http://localhost:3000/api. Il faut vérifier que le backend écoute réellement sur le port 3000.

Dans certaines parties du projet, le backend a également été utilisé sur le port 5000. Il faut donc utiliser un seul port cohérent entre le frontend et le backend.

Les routes protégées doivent recevoir correctement le token JWT.

Le nom des champs retournés par le backend doit correspondre aux noms utilisés dans React.

68. Point important concernant le statut de commande

Dans AdminOrders, le statut de commande est appelé orderStatus.

Dans AdminPayments, le code cherche actuellement payment.orderId.status.

Si le modèle Order utilise réellement orderStatus, il faudra utiliser : payment.orderId.orderStatus dans AdminPayments.

69. Sécurité

Les opérations sensibles comme la modification et la suppression doivent être protégées côté backend.

Le frontend ne doit pas être considéré comme la seule protection.

Même si un bouton de suppression est caché dans React, un utilisateur pourrait essayer d'appeler directement l'API.

Le backend doit donc vérifier le JWT et le rôle de l'utilisateur avant d'autoriser les opérations administratives.

70. Conclusion

Les composants AdminOrders, AdminProducts et AdminPayments constituent les principales interfaces de gestion de la boutique côté administrateur.

AdminOrders permet de gérer les commandes et leurs statuts.

AdminProducts permet de gérer les produits, les prix, les catégories et surtout le stock.

AdminPayments permet de suivre les transactions Stripe et leur état.

L'ensemble fonctionne grâce à une architecture React, Axios, Node.js, Express, Mongoose et MongoDB, avec une authentification JWT pour sécuriser les opérations administratives.

L'espace administrateur permet donc de centraliser la gestion commerciale de la boutique : produits, commandes, paiements et suivi des ventes.
