Explication de l'Interface Administration Pharma

1. Présentation générale

Cette partie du projet correspond à l'interface d'administration de la plateforme Pharma. Elle est développée avec React et permet à l'administrateur de gérer les produits, les commandes, les paiements, les ventes, les paramètres et les clients.

L'interface communique avec le backend grâce à Axios. Le backend fournit des API REST développées avec Node.js et Express.

Le fonctionnement général est donc :

React ↓ Axios ↓ API Express ↓ Controllers ↓ MongoDB

2. Composant AdminCustomers

Le composant AdminCustomers représente la page permettant à l'administrateur de consulter et de supprimer les clients enregistrés sur la plateforme.

Il utilise les hooks React useState et useEffect.

3. Importation de useEffect et useState

Le code commence par importer useEffect et useState depuis React.

useState permet de créer et modifier les données internes du composant.

useEffect permet d'exécuter automatiquement une fonction lorsque le composant est chargé.

4. Importation de Axios

Axios est utilisé pour envoyer des requêtes HTTP au backend.

Dans ce composant, Axios permet notamment de récupérer la liste des clients et de supprimer un client.

5. URL de l'API

La constante API contient l'adresse principale du backend :

http://localhost:3000/api

Toutes les requêtes de ce composant utilisent cette adresse comme base.

6. State customers

Le state customers contient la liste des clients récupérés depuis MongoDB.

Il est initialisé avec un tableau vide :

const [customers, setCustomers] = useState([]);

setCustomers permet de modifier cette liste.

7. State loading

Le state loading permet de savoir si les données sont encore en cours de chargement.

Il commence à true. Pendant cette période, l'utilisateur voit le message Chargement des clients....

8. State error

Le state error permet de stocker un éventuel message d'erreur.

S'il existe une erreur lors de la communication avec le backend, le message est affiché à l'administrateur.

9. Fonction fetchCustomers

La fonction fetchCustomers permet de récupérer la liste des clients depuis le backend.

Elle commence par activer le chargement avec :

setLoading(true);

Puis elle réinitialise l'ancien message d'erreur avec :

setError("");

10. Requête GET des clients

Axios envoie ensuite une requête GET vers :

GET /api/users/customers

Le backend retourne les clients enregistrés.

Si la réponse contient success: true, la liste response.data.customers est enregistrée dans le state customers.

11. Gestion d'une réponse sans clients

Si le backend retourne une réponse négative, le tableau des clients est réinitialisé et un message d'erreur est affiché.

Cela permet d'éviter d'afficher d'anciennes données lorsque la requête échoue.

12. Gestion des erreurs Axios

Le bloc catch récupère les erreurs provenant de la requête HTTP.

Le code essaie d'abord de récupérer le message envoyé par le backend avec : error.response?.data?.message.

Si aucun message n'est disponible, un message général est affiché.

13. Bloc finally

Le bloc finally est exécuté que la requête réussisse ou échoue.

Il permet de désactiver le chargement avec :

setLoading(false);

14. useEffect pour charger les clients

Le hook useEffect appelle automatiquement fetchCustomers() lorsque la page est chargée.

Le tableau vide [] signifie que cette fonction est exécutée une seule fois au montage du composant.

15. Suppression d'un client

La fonction handleDelete permet de supprimer un client. Elle reçoit l'identifiant MongoDB du client.

16. Confirmation avant suppression

Avant de supprimer le client, le code utilise :

window.confirm(...)

Une fenêtre de confirmation demande à l'administrateur s'il souhaite réellement supprimer le client.

Si l'administrateur choisit d'annuler, la fonction s'arrête immédiatement.

17. Requête DELETE

Si l'administrateur confirme, Axios envoie une requête DELETE vers :

DELETE /api/users/customers/:id

L'identifiant du client est placé dans l'URL.

18. Suppression immédiate dans React

Lorsque le backend confirme la suppression, le client est également supprimé du tableau React.

Le code utilise la fonction filter() pour conserver tous les clients sauf celui qui vient d'être supprimé.

Cela permet de mettre à jour immédiatement l'interface sans devoir recharger toute la page.

19. État Loading dans AdminCustomers

Lorsque loading est égal à true, le composant affiche une page simple contenant le titre Customers et le message Chargement des clients....

20. État Error dans AdminCustomers

Lorsque le state error contient un message, la page affiche une zone d'erreur.

Un bouton Réessayer permet de rappeler fetchCustomers() afin de refaire la requête.

21. Affichage du nombre de clients

Lorsque les données sont chargées, le composant affiche le nombre total de clients avec :

customers.length

Cela permet à l'administrateur de connaître immédiatement le nombre de clients présents dans la base de données.

22. Affichage lorsqu'il n'y a aucun client

Si le tableau customers est vide, le composant affiche Aucun client.

Il précise également que les utilisateurs ayant le rôle user n'ont pas été trouvés.

23. Tableau des clients

Lorsque des clients existent, ils sont affichés dans un tableau HTML.

Le tableau contient les colonnes ID, Username, Email, Role, Inscription et Actions.

24. Fonction map

La fonction map() permet de parcourir tous les clients et de créer une ligne HTML pour chaque client.

Chaque ligne possède comme clé l'identifiant unique MongoDB du client.

25. Affichage de l'ID

Le code utilise :

customer._id.slice(-8)

Cela permet d'afficher uniquement les huit derniers caractères de l'identifiant MongoDB afin de rendre le tableau plus lisible.

26. Affichage du username

Le nom d'utilisateur est affiché avec :

customer.username

Il est placé dans une balise strong afin de le mettre en évidence.

27. Affichage de l'email

L'adresse email du client est affichée avec :

customer.email

28. Affichage du rôle

Le rôle est affiché dans un badge grâce à :

customer.role

Dans cette page, les clients récupérés sont normalement ceux qui possèdent le rôle user.

29. Affichage de la date d'inscription

Le code vérifie si createdAt existe. Si cette valeur existe, elle est convertie en objet Date JavaScript.

La méthode toLocaleDateString("fr-FR") permet d'afficher la date selon le format français.

30. Bouton Supprimer

Chaque ligne contient un bouton permettant de supprimer le client.

Lorsque l'administrateur clique sur ce bouton, la fonction handleDelete(customer._id) est exécutée.

31. Composant AdminDashboard

Le composant AdminDashboard représente la page principale du tableau de bord administrateur.

Il rassemble plusieurs informations importantes de la boutique : produits, commandes, paiements, ventes et paramètres.

32. Importation d'AdminNavbar

Le composant importe AdminNavbar. Cette barre de navigation permet à l'administrateur de se déplacer entre les différentes pages de l'administration.

33. State products

Le state products contient la liste des produits récupérés depuis l'API.

Le nombre de produits est ensuite calculé avec :

products.length

34. State orders

Le state orders contient la liste des commandes.

Le nombre total de commandes est affiché dans la carte Commandes.

35. State payments

Le state payments contient la liste des paiements.

Cette liste est également utilisée pour calculer le nombre de paiements payés et en attente.

36. State sales

Le state sales contient trois statistiques : le chiffre d'affaires total, le nombre de commandes et le panier moyen.

Les valeurs initiales sont toutes égales à zéro.

37. State settings

Le state settings contient les paramètres de la boutique récupérés depuis le backend.

Il est initialisé avec null car les paramètres ne sont pas encore chargés au démarrage.

38. Récupération du token JWT

Lors du chargement du dashboard, le token est récupéré depuis localStorage.

localStorage.getItem("token")

Ce token permet au frontend de prouver au backend que l'utilisateur est authentifié.

39. Création du header Authorization

Le token est ensuite placé dans l'en-tête HTTP Authorization.

Authorization: Bearer TOKEN

Ce format correspond au fonctionnement du middleware JWT du backend.

40. Récupération des produits dans le Dashboard

Le dashboard envoie une requête GET vers :

GET /api/products

Cette route est publique dans ton backend. Il n'est donc pas obligatoire d'envoyer le token pour cette requête.

La réponse est ensuite vérifiée afin de déterminer si elle contient directement un tableau ou si les produits se trouvent dans une propriété products ou data.

41. Récupération des commandes

Le dashboard appelle :

GET /api/orders

Cette route est protégée par auth et isAdmin.

Le token JWT est donc envoyé dans les headers.

42. Récupération des paiements

Le dashboard appelle :

GET /api/payments/admin

Cette route est réservée aux administrateurs. Le token JWT est envoyé avec la requête.

43. Récupération des statistiques de ventes

Le dashboard appelle :

GET /api/sales/overview

Le backend calcule le chiffre d'affaires, le nombre de commandes et le panier moyen.

Ces valeurs sont ensuite enregistrées dans le state sales.

44. Récupération des paramètres

Le dashboard appelle :

GET /api/settings

Cette route est protégée par auth et isAdmin.

Les paramètres récupérés sont stockés dans le state settings.

45. Fonction formatMoney

La fonction formatMoney permet de formater les montants financiers.

Elle utilise toLocaleString("fr-FR") afin d'obtenir un format adapté à la langue française.

Le nombre possède toujours deux chiffres après la virgule.

46. Statistiques des paiements payés

La constante paidPayments utilise la fonction filter() pour compter les paiements dont le statut est paid.

Elle permet donc d'afficher le nombre de paiements réussis.

47. Statistiques des paiements en attente

La constante pendingPayments fait la même chose pour les paiements ayant le statut pending.

48. Admin Dashboard : carte Produits

La première carte du dashboard affiche le nombre total de produits.

La valeur affichée correspond à :

products.length

L'icône utilisée est l'icône de boîte représentant les produits.

49. Admin Dashboard : carte Commandes

La deuxième carte affiche le nombre total de commandes.

La valeur correspond à :

orders.length

50. Admin Dashboard : carte Paiements

La troisième carte affiche le nombre total de paiements.

Elle affiche également le nombre de paiements ayant le statut paid.

51. Admin Dashboard : carte Ventes

La carte Ventes affiche le chiffre d'affaires total.

Le montant provient du backend grâce à l'API /api/sales/overview.

Le montant est formaté avec formatMoney() puis affiché en TND.

52. Admin Dashboard : carte Settings

La carte Settings indique si la boutique est actuellement active ou en mode maintenance.

Si maintenanceMode est vrai, le dashboard affiche Maintenance.

Sinon, il affiche Actif.

La carte affiche également si Stripe est activé ou désactivé grâce à settings.stripeEnabled.

53. Résumé des ventes

La section Résumé des ventes présente trois informations principales.

La première est le chiffre d'affaires total. La deuxième est le nombre de commandes payées. La troisième est le panier moyen.

54. Chiffre d'affaires

Le chiffre d'affaires est récupéré depuis :

sales.totalSales

Il est ensuite formaté et affiché avec la devise TND.

55. Commandes payées

Le nombre de commandes payées correspond à :

sales.totalOrders

Cette valeur provient directement du contrôleur des statistiques de ventes.

56. Panier moyen

Le panier moyen correspond à la valeur :

sales.averageOrder

Il représente le montant moyen d'une commande.

57. Résumé des paiements

La section Résumé des paiements présente trois informations : le nombre total de paiements, les paiements réussis et les paiements en attente.

Cela permet à l'administrateur d'avoir rapidement une vision de la situation des paiements.

58. Styles du Dashboard

Le composant utilise un objet JavaScript appelé styles pour définir directement plusieurs styles CSS.

Par exemple, styles.page définit l'espace intérieur, la couleur de fond et la hauteur minimale de la page.

styles.cards utilise CSS Grid afin d'organiser les cartes du dashboard en plusieurs colonnes.

Le composant AdminNavbar représente la barre de navigation de l'administration.

Il permet d'accéder rapidement aux différentes fonctionnalités du dashboard.

60. useNavigate

Le hook useNavigate de React Router permet de modifier programmatiquement la page actuelle.

Il est principalement utilisé ici lors de la déconnexion.

La fonction handleLogout permet de déconnecter l'utilisateur.

Elle supprime le token JWT du navigateur avec :

Enfin, l'utilisateur est redirigé vers :

/auth

La navigation permet donc de passer entre les principales fonctionnalités du panneau administrateur.

Dashboard Products Orders Payments Sales Settings Customers Logout

72. Communication entre AdminDashboard et le backend

Le dashboard récupère plusieurs catégories de données auprès du backend. Chaque catégorie correspond à une API différente.

Products → GET /api/products Orders → GET /api/orders Payments → GET /api/payments/admin Sales → GET /api/sales/overview Settings → GET /api/settings

73. Communication entre AdminCustomers et le backend

La page Customers utilise principalement deux opérations.

GET /api/users/customers DELETE /api/users/customers/:id

La première récupère les clients et la deuxième supprime un client.

74. Correspondance avec le backend

Les routes React correspondent directement aux routes Express définies dans le backend.

Par exemple, la route frontend Axios GET /api/orders correspond à la route Express protégée par auth et isAdmin.

Cela signifie que le backend vérifie le token JWT avant d'autoriser l'accès aux commandes administratives.

75. Sécurité avec JWT

Le token JWT est essentiel pour les fonctionnalités administratives. Il est récupéré depuis le localStorage et envoyé dans le header Authorization.

Le middleware backend auth vérifie le token. Ensuite, isAdmin vérifie que le rôle de l'utilisateur est bien admin.

Le principe de sécurité est donc : utilisateur connecté → token valide → vérification du rôle admin → accès au dashboard.

76. Point important concernant AdminCustomers

Dans ton frontend, la page Customers appelle directement :

GET /api/users/customers

et :

DELETE /api/users/customers/:id

Dans les routes backend que tu as montrées précédemment, ces deux routes n'utilisent actuellement ni auth ni isAdmin.

Pour une application réelle, il est préférable de protéger ces routes afin qu'un utilisateur normal ne puisse pas consulter ou supprimer les comptes des autres clients.

77. Protection recommandée des routes Customers

Les routes administratives des clients devraient idéalement fonctionner avec le même principe que les autres routes du dashboard :

router.get( "/customers", auth, isAdmin, getCustomers ); router.get( "/customers/:id", auth, isAdmin, getCustomerById ); router.delete( "/customers/:id", auth, isAdmin, deleteCustomer );

De cette manière, seul un administrateur authentifié pourra consulter et supprimer les clients.

78. Flux complet de l'administration

Lorsque l'administrateur ouvre le dashboard, React charge le composant AdminDashboard.

Le composant récupère le token JWT dans localStorage.

Ensuite, plusieurs requêtes Axios sont envoyées au backend afin de récupérer les produits, commandes, paiements, statistiques et paramètres.

Le backend vérifie les droits lorsque cela est nécessaire et récupère les données dans MongoDB.

Les résultats sont retournés à React. React stocke les résultats dans ses states puis les affiche sous forme de cartes et de statistiques.

79. Flux complet pour les clients

Lorsque l'administrateur ouvre la page Customers, le composant AdminCustomers est chargé.

Le hook useEffect appelle automatiquement fetchCustomers().

Axios envoie une requête GET au backend. Le backend récupère les utilisateurs ayant le rôle user.

React reçoit la liste et l'affiche dans un tableau.

Lorsque l'administrateur clique sur Supprimer, Axios envoie une requête DELETE. Après confirmation du backend, le client est retiré immédiatement de l'interface.

80. Architecture générale

L'architecture de cette partie de l'application peut être résumée ainsi :

ADMIN ↓ React Admin Panel ↓ React Router ↓ Axios ↓ Express API ↓ JWT Middleware ↓ Admin Middleware ↓ Controllers ↓ Mongoose ↓ MongoDB

81. Conclusion

Cette partie du projet constitue le panneau d'administration de la plateforme Pharma.

AdminNavbar permet de naviguer entre les différentes pages.

AdminDashboard fournit une vue globale de la boutique avec les produits, commandes, paiements, ventes et paramètres.

AdminCustomers permet de consulter et supprimer les clients.

Axios assure la communication entre React et l'API backend.

JWT assure l'authentification et permet au backend de vérifier l'identité de l'utilisateur.

isAdmin permet de réserver les opérations sensibles aux administrateurs.

L'ensemble permet donc de construire une interface d'administration complète pour gérer une boutique pharmaceutique en ligne.
