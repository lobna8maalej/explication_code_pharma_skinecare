Store Administration Documentation

This documentation explains in detail how the React components used in the store administration area work.

The components covered are AdminOrders, AdminProducts and AdminPayments.

These components allow the administrator to manage orders, products, inventory and payments made with Stripe.

1. General Architecture

The application uses React to build the administration user interface. React communicates with the backend using the Axios library.

The frontend sends HTTP requests to the backend API available at: http://localhost:3000/api.

The backend receives the requests, performs the necessary operations, communicates with MongoDB and returns the results to the frontend.

React Admin → Axios → API Express/Node.js → MongoDB

For certain administrative operations, a JWT token is retrieved from localStorage and then sent in the HTTP Authorization header.

2. AdminOrders Component

The AdminOrders component represents the administration page dedicated to managing customer orders.

The administrator can view orders, see customer information, view ordered products, check the total amount, view the payment, modify the order status and delete an order.

3. Importing Dependencies in AdminOrders

The component begins by importing the React hooks useEffect and useState.

useState is used to manage the dynamic data of the page, while useEffect is used to execute code when the component is loaded.

Axios is used to communicate with the backend.

The component also imports AdminNavbar to display the administration navigation bar.

The AdminOrders.css file contains the styles specific to the orders page.

4. API Used by AdminOrders

The API constant contains the main backend address. 

const API = "http://localhost:3000/api";

All order requests are then built from this address.

5. Order State

The component uses three main states: orders, loading and error.

orders contains the list of orders retrieved from the backend.

loading indicates whether the orders are currently being loaded.

error may contain the error message to display when retrieving the orders fails.

6. Retrieving Orders

The fetchOrders function retrieves all orders from the API.

Before making the request, the component retrieves the administrator token stored in localStorage. 

const token = localStorage.getItem("token");

The token is sent to the backend using the following header: Authorization: Bearer token.

This method allows the backend to verify that the request comes from an authenticated user.

7. GET Request for Orders

The following request is used to retrieve all orders: 

axios.get(`${API}/orders`, {
  headers: {
    Authorization: `Bearer ${token}`,
  },
});

The backend must then return the orders in the orders property or possibly in data.

The frontend then verifies that the result is actually an array before storing it in orders.

8. useEffect in AdminOrders

The useEffect hook is used with an empty dependency array. 

useEffect(() => {
  fetchOrders();
}, []);

This means that fetchOrders is executed only once when the page is loaded.

9. Changing the Status of an Order

The updateStatus function allows the administrator to change the status of an order.

The order ID and the new status are sent to the backend. 

axios.put(
  `${API}/orders/${orderId}/status`,
  {
    orderStatus: newStatus,
  },
  {
    headers: {
      Authorization: `Bearer ${token}`,
    },
  }
);

The new status can be, for example: En attente, En préparation, Expédiée, Livrée or Annulée.

10. Immediate Interface Update

After the status is successfully modified, the frontend does not necessarily reload the entire list from the server.

It directly updates the relevant order in the orders state.

This technique provides a faster and more responsive interface.

11. Deleting an Order

The deleteOrder function allows an order to be deleted.

Before deletion, a confirmation dialog is displayed using window.confirm.

If the administrator confirms, an HTTP DELETE request is sent to the backend. 

axios.delete(`${API}/orders/${orderId}`, {
  headers: {
    Authorization: `Bearer ${token}`,
  },
});

After deletion, the order is also removed from the orders state.

12. Retrieving the Customer Name

The getCustomerName function determines the name of the customer associated with an order.

The component first checks the information available in order.customer.

If the first name or last name exists, they are combined to form the full name.

If this information is not available, the component uses order.user.username.

If no information is available, the text Client inconnu is displayed.

13. Retrieving the Customer Email

The getCustomerEmail function looks for the email in order.customer.email.

If this value does not exist, it uses order.user.email.

If no address is available, the text Email inconnu is displayed.

14. Retrieving the Products of an Order

The getItems function checks whether the order contains an items array.

If this array does not exist, it also checks the products property.

This logic makes the component more flexible when a different structure is returned by the backend.

15. Calculating the Total Amount

The getTotal function retrieves the total amount of the order.

It first uses totalAmount.

If this property does not exist, it uses totalPrice.

If no value is available, the default amount is 0.

16. Payment Status

The getPaymentStatus function retrieves the payment status.

If no status is available, the default value is En attente.

This prevents an empty value from being displayed in the interface.

17. Order Status

The getOrderStatus function retrieves the current status of the order.

If the backend does not provide a status, the value En attente is used.

18. Date Formatting

The formatDate function transforms a date coming from MongoDB into a date that is readable by the user.

The format used is French thanks to toLocaleDateString("fr-FR").

A date can therefore be displayed in the form 07/09/2026.

19. Loading Management

When loading is true, the component displays a message indicating that the orders are being loaded.

The AdminNavbar navigation bar also remains visible.

20. Error Management

If an error occurs while retrieving the orders, the message is stored in error.

The user then sees an error message along with a Réessayer button.

The button allows the fetchOrders function to be executed again without manually reloading the page.

21. Displaying an Order

Each order is displayed as a card using the order-card class.

The card contains several pieces of information: order number, date, customer, email, phone number, address, products, amount, payment and status.

22. Displaying Products

For each ordered product, the component retrieves the name, price and quantity.

The subtotal is then calculated using the following formula: 

Subtotal = Price × Quantity

The result is displayed with two decimal places.

23. Changing the Status with a Select

The administrator has an HTML select element that allows them to choose the new status.

When the value changes, the updateStatus function is automatically called.

This makes it possible to quickly change the status of an order directly from the management table.

24. AdminProducts Component

The AdminProducts component allows the administrator to manage the store's products.

It allows the administrator to view products, modify their information, increase or decrease stock and delete a product.

25. Product State

The products state contains the list of products.

The loading state indicates whether the products are still being retrieved.

The editingProduct state contains the product currently selected for editing.

26. Edit Form States

Several states are used to manage the form fields: name, price, stock and category.

Each field is controlled by React. When the user types into a field, its corresponding state is automatically updated.

27. Retrieving Products

The fetchProducts function sends a GET request to /products. 

axios.get(`${API}/products`);

The component accepts several possible response formats: an array directly, products or data.

28. Quick Stock Update

The updateStock function allows the stock of a product to be modified directly from the list.

Before sending the request, the component checks that the new stock is not negative.

The new stock is then sent to the backend with a PUT request. 

axios.put(
  `${API}/products/${productId}`,
  {
    stock: Number(newStock)
  }
);

29. Protection Against Negative Stock

The code deliberately prevents the creation of stock below zero.

When the stock is equal to zero, the button used to decrease the stock is disabled.

This check is important to ensure the consistency of commercial data.

30. Plus and Minus Stock Buttons

The decreaseStock function decreases the stock by one unit.

The increaseStock function increases the stock by one unit.

Both functions then call updateStock to send the new value to the backend.

31. Stock Level Indicator

The component uses three stock levels.

When the stock is equal to zero, the interface displays Rupture.

When the stock is greater than zero but less than or equal to five, the interface displays Stock faible.

When the stock is greater than five, the interface displays En stock.

32. Opening the Edit Form

The handleEdit function is called when the administrator clicks the Modifier button.

It stores the selected product in editingProduct and copies its values into the different form fields.

33. Canceling the Edit

The handleCancelEdit function closes the edit form.

It also resets the fields name, price, stock and category to their initial values.

34. Product Form Validation

Before modifying a product, the code checks that all required fields have been filled in.

The name must not be empty, the price must be provided, the stock must be provided and a category must be selected.

The price and stock cannot be negative.

35. Saving an Edited Product

The handleUpdate function sends the new information to the backend using a PUT request. 

axios.put(
  `${API}/products/${editingProduct._id}`,
  {
    name: name.trim(),
    price: Number(price),
    stock: Number(stock),
    category
  }
);

After the update, the form is closed and fetchProducts() is executed to retrieve the updated data.

36. Deleting a Product

The handleDelete function allows a product to be deleted.

Confirmation is requested from the administrator before executing the DELETE request. 

axios.delete(`${API}/products/${productId}`, {
  headers: {
    Authorization: `Bearer ${token}`
  }
});

Once the deletion is successful, the product is removed from the products state.

37. Displaying the Product Table

Products are displayed in an HTML table.

The main columns are product, price, stock, category and actions.

For each product, React uses product._id as the unique key for the row.

38. AdminPayments Component

The AdminPayments component is designed to manage payments made by customers.

In this application, payments are associated with Stripe.

The administrator can view the total number of payments, successful payments, pending payments and failed payments.

39. Payment State

The payments state contains the list of payments retrieved from the backend.

The loading state indicates whether payments are currently being retrieved.

The error state contains the possible error message.

40. Retrieving Payments

The fetchPayments function retrieves payments from the /payments/admin endpoint. 

axios.get(`${API}/payments/admin`, {
  headers: {
    Authorization: `Bearer ${token}`
  }
});

This route is intended for administration and therefore requires an authentication token.

41. Checking the Administrator Token

Before contacting the API, the component checks whether the token exists in localStorage.

If no token is found, a message indicates that the administrator token cannot be found.

This check prevents an unnecessary request from being sent to a protected route.

42. Payment Statistics

The component directly calculates several statistics from the payments array.

payments.length represents the total number of payments.

payments.filter(payment => payment.status === "paid").length counts successful payments.

Payments whose status is pending are counted as pending payments.

Payments whose status is failed are counted as failed payments.

43. Displaying the Payment Customer

For each payment, the component displays the username from payment.userId.username.

The email address is retrieved from payment.userId.email.

If this information is not available, default values are displayed.

44. Payment and Order Association

Each payment can be associated with an order through payment.orderId.

The component displays the last characters of the order's MongoDB identifier.

Using slice(-8) makes it possible to display only the last eight characters of the identifier, making the display shorter.

45. Displaying the Payment Amount

The amount is converted to a number using Number().

Then, toFixed(2) displays exactly two decimal places.

The currency from payment.currency is converted to uppercase using toUpperCase().

For example, the currency usd becomes USD.

46. Payment Method

The component currently displays Stripe as the payment method.

A visual badge using the stripe-badge class is used to distinguish this method.

47. Payment Status

The payment status can be paid, pending, failed or refunded.

The frontend transforms these technical values into French text.

paid becomes Payé.

pending becomes En attente.

failed becomes Échec.

refunded becomes Remboursé.

48. Status of the Associated Order

The component also attempts to display the status of the order associated with the payment.

This information is retrieved from payment.orderId.status.

It is important to verify that the backend actually uses the name status for the order status.

In the order controller presented previously, the field used is rather orderStatus. If the backend returns orderStatus, the frontend must use payment.orderId.orderStatus.

49. Displaying the Payment Date

The date is retrieved from payment.createdAt.

It is converted to the French format using toLocaleDateString("fr-FR").

50. Refresh Button

The Actualiser button allows the administrator to manually run the fetchPayments function again.

This makes it possible to immediately obtain the latest information from the backend without reloading the entire application.

51. Handling Empty Payments

When the payments array is empty, the component displays the message Aucun paiement trouvé..

The message occupies all seven table columns through colSpan="7".

52. Handling Payment Loading

When payments are still being loaded, the user sees the text Chargement des paiements....

This prevents the user from thinking that the page is empty when the data is simply being retrieved.

53. Handling Payment Errors

If the request fails, the component retrieves the message provided by the backend through error.response?.data?.message.

If no backend message is available, a generic message is displayed.

The Réessayer button can then be used to retry the retrieval.

54. JWT Authentication

The administration components use a JWT token stored in localStorage.

The token is sent in the header: Authorization: Bearer token.

The backend can then use this token to identify the logged-in user and control their permissions.

55. Communication with MongoDB

The React frontend does not communicate directly with MongoDB.

React sends an HTTP request to the Node.js/Express server.

The server then uses Mongoose to communicate with MongoDB.

Admin → React → Axios → Express → Controller → Mongoose → MongoDB

56. Order Management Cycle

When an order is created by a customer, it is stored in MongoDB.

The administrator then opens the AdminOrders page.

React requests the orders from the backend.

The backend retrieves the orders from MongoDB and returns them to the frontend.

The administrator can then modify the status or delete an order.

57. Product Management Cycle

The administrator opens AdminProducts.

The frontend retrieves the products from the API.

The administrator can modify the name, price, stock and category.

They can also quickly modify the stock using the + and − buttons.

All modifications are then saved in MongoDB through the backend API.

58. Payment Management Cycle

When a customer makes a payment with Stripe, the backend stores the payment information.

The payment can then be viewed from AdminPayments.

The administrator can see the customer, order, amount, currency, payment status and date.

59. Relationship Between Orders and Payments

An order contains information about its payment, including its payment status.

The payment also contains a reference to the order through orderId.

This makes it possible to link both pieces of information and track the complete sales process.

60. Relationship Between Products and Orders

An order contains a list of products in items.

Each item may contain a product, its name, its price and its quantity.

This allows the administration area to know exactly which products have been ordered.

61. Role of AdminNavbar

The AdminNavbar component represents the main navigation of the administrator area.

It contains links to the Dashboard, products, orders, payments, sales, settings and customers.

The component uses Link from React Router to navigate between the different pages without completely reloading the application.

62. Administrator Logout

The handleLogout function removes the token and user information stored in localStorage. 

localStorage.removeItem("token");
localStorage.removeItem("user");

The user is then redirected to the /auth page.

63. AdminOrders Summary

AdminOrders is responsible for the complete management of orders from the administration area.

It retrieves orders, displays customer information, displays products, calculates subtotals, displays payments, allows the status to be modified and allows an order to be deleted.

64. AdminProducts Summary

AdminProducts allows the product catalog to be managed.

It allows the administrator to view products, modify their information, control their stock and delete products.

65. AdminPayments Summary

AdminPayments allows Stripe payments made by customers to be monitored.

It provides payment statistics and displays detailed information about each transaction.

67. Important Points to Check

The frontend currently uses http://localhost:3000/api. You must verify that the backend is actually listening on port 3000.

In some parts of the project, the backend has also been used on port 5000. Therefore, a single consistent port must be used between the frontend and backend.

Protected routes must correctly receive the JWT token.

The names of the fields returned by the backend must match the names used in React.

68. Important Point Regarding the Order Status

In AdminOrders, the order status is called orderStatus.

In AdminPayments, the code currently looks for payment.orderId.status.

If the Order model actually uses orderStatus, you will need to use: payment.orderId.orderStatus in AdminPayments.

69. Security

Sensitive operations such as modification and deletion must be protected on the backend.

The frontend must not be considered the only layer of protection.

Even if a delete button is hidden in React, a user could try to call the API directly.

The backend must therefore verify the JWT and the user's role before authorizing administrative operations.

70. Conclusion

The AdminOrders, AdminProducts and AdminPayments components constitute the main administration interfaces for managing the store.

AdminOrders allows orders and their statuses to be managed.

AdminProducts allows products, prices, categories and, above all, stock to be managed.

AdminPayments allows Stripe transactions and their status to be monitored.

The entire system works through an architecture based on React, Axios, Node.js, Express, Mongoose and MongoDB, with JWT authentication to secure administrative operations.

The administration area therefore makes it possible to centralize the store's commercial management: products, orders, payments and sales monitoring.
